## 根本的なボトルネック

### 1. コンテキスト限界（~100-120K tokens）

Docker ビルドと bundle update の出力がコンテキストを圧迫し、テスト追加 + アップグレードの両方を1セッションで完了するのが困難。

- テスト追加: ~30-50K tokens
- Rails アップグレード + Docker ビルド: ~40-70K tokens
- 合計: 70-120K tokens

**対策案:**
1. Docker 出力の `| tail -N` を必須化
2. テスト追加とアップグレードを別セッションに分割
3. opencode の compaction をアップグレード前に挿入

### 2. ローカルLLM の知識カットオフ

Qwen3.5-35B が最新の gem バージョンや Ruby/Rails の要件を知らない場合がある。CLAUDE.md で明示的に情報を提供することで対処可能。

### 3. plan_exit 呼び出しの不安定さ

ローカルLLM がテキスト応答でツール呼び出しを代替する傾向。プロンプトに明記することで改善されるが、100% ではない。

## 推奨事項

### opencode 開発チームへ

1. **Docker/Bash 出力のトリミング**: 長いコマンド出力を自動的にトリミングする機能
2. **plan_exit の強制**: plan mode で応答を終了する前に plan_exit が呼ばれていない場合の警告
3. **コンテキスト管理の改善**: 一定のトークン数に達したら自動 compaction

### スキル開発者へ

1. **具体的な制約を書く**: 「bundle update を使え」ではなく「`./docker_compose --profile test run --rm test bash -c "bundle update rails"` を実行」
2. **バージョン情報を明記**: ローカルLLM は知識カットオフがあるため、具体的なバージョン番号と要件を CLAUDE.md に記載
3. **失敗パターンを制約に変換**: 各イテレーションで発見した失敗パターンを「〜しないこと」の制約に変換
