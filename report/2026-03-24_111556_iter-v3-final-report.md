## v2 → v3 の主要変更と効果

### 1. bash.txt timeout テンプレート変数化
- **変更**: `120000ms (2 minutes)` → `${defaultTimeoutMs}ms (${defaultTimeoutMinutes} minutes)`
- **効果**: LLM が 10分と認識し、短い timeout 設定を回避。ただし `--no-cache` 問題は別途対策が必要だった

### 2. upgrade スクリプト（iter 29 で導入）
- **変更**: Docker build の全手順をスクリプト化
- **効果**: テスト実行率 0% → 82% に劇的改善。LLM がテスト追加に集中できるようになった

#### 導入経緯

iter 23-29 の 7 回連続で LLM は Docker build に失敗し、テストを一度も実行できなかった。主な失敗パターン:
- CLAUDE.md で禁止しているにも関わらず `--no-cache` を繰り返し付与し、10分超のビルドでタイムアウト
- `docker rmi` でイメージを削除してゼロからリビルドを試みる
- bootsnap キャッシュの残存により Rails 起動時に LoadError が発生
- sprockets-rails の互換性問題で行き詰まり、`config/boot.rb` を改変（制約違反）

CLAUDE.md に「`--no-cache` を付けない」「`docker rmi` を使わない」等の禁止指示を繰り返し追加したが、LLM は Docker に関する事前知識（キャッシュ問題は `--no-cache` で解決するという常識）を優先し、指示を無視する傾向が続いた。

#### スクリプトの具体内容

`ytdlor/.claude/scripts/upgrade_to_rails81.sh` として配置。4ステップで構成:

1. **ファイル更新**: `.ruby-version`、`Dockerfile`（Ruby イメージタグ）、`Gemfile`（Ruby バージョン・Rails バージョン・minitest ピン）、`config/application.rb`（`load_defaults`）を `sed` で一括書き換え
2. **Gemfile.lock 更新**: 一時的な Ruby コンテナ（`docker run --rm`）内で `bundle update rails minitest sprockets-rails` を実行し、ホスト側の `Gemfile.lock` を更新
3. **Docker image rebuild**: `./docker_compose build test` でテスト用イメージをリビルド（キャッシュ有効）
4. **bootsnap キャッシュクリア**: bind mount 経由で `tmp/cache/bootsnap` を削除し、古い Rails バージョンのキャッシュによる LoadError を防止

#### 作成主体

スクリプトはメインの Claude（Opus）が iter 29 までの失敗パターンを分析して作成した。opencode TUI 内で動作するローカル LLM（Qwen3.5-35B-A3B）が作成したものではない。iter 29 の失敗後、Docker build で LLM が繰り返し躓くポイント（ファイル書き換えの順序、Gemfile.lock の更新方法、bootsnap キャッシュ）を特定し、これらを1コマンドで実行できるシェルスクリプトとしてまとめた。

#### 配置場所と参照方法

- スクリプト: `ytdlor/.claude/scripts/upgrade_to_rails81.sh`
- CLAUDE.md に「Docker 環境での Rails アップグレード手順」セクションを設け、`bash .claude/scripts/upgrade_to_rails81.sh` の1行で手順を完結させる指示を記載
- プロンプトにも同じコマンドを明記し、LLM が個別のステップを手動実行しないよう誘導
- iter 30 後に Ruby 3.3.0 → 3.4.1 への切り替えが必要と判明し、スクリプト内の Ruby バージョンも更新（コミット `cecce0f`）

### 3. Ruby 3.4.1 への切り替え（iter 30 後の調査で発見）
- **変更**: Ruby 3.3.0 → 3.4.1
- **理由**: Rails 8.1.2 の actionview が anonymous rest parameter を使用し Ruby 3.3.x で SyntaxError
- **効果**: sprockets-rails LoadError の根本解決

### 4. プロダクションコード変更の定性評価
- **変更**: 一律禁止 → Rails 互換性のための最小変更は許可
- **結果**: `app/` 変更があった iter は 33,38,40,41,45,47,49,51 の 8 回
  - 妥当: `processing?`/`failed?` メソッド追加、`format_status_badge` ヘルパー追加
  - 違反: コントローラーアクションのアンコメント（iter 33,45,49,51）

## 発見と知見

### 1. CLAUDE.md 累積改善の効果と限界
- 30 回のイテレーションで 12 回の CLAUDE.md 改善を実施
- CLAUDE.md は「LLM が正しい判断をする確率を上げる」効果がある
- しかし「環境の根本問題」（Ruby 互換性、vendor/bundle 残存）は CLAUDE.md では解決できない
- **根本原因の直接調査・修正** が必要な場面がある

### 2. ローカル LLM の特性
- **事前知識の優先**: `--no-cache` を繰り返す（Docker の常識が CLAUDE.md の指示を上書き）
- **RSpec 構文の混入**: Minitest プロジェクトでも RSpec メソッドを使う傾向
- **アンコメント傾向**: テストを通すためにコメントアウトされたコードを復活させる
- **Compaction 後の計画喪失**: Build phase でテスト追加をスキップ

### 3. Rolling Truncation の影響
- v2 では Rolling Truncation が Docker 出力のコンテキスト圧迫を緩和
- v3 では Truncation 回数が増加（平均 37回 vs v2 の平均 50回）
- Context 100% 到達時に Compaction エラーが発生するケースあり（iter 45, 52）

### 4. upgrade スクリプトの有効性
- Docker build の複雑さを完全に隠蔽
- LLM の「試行錯誤」を排除し、確実にアップグレードを実行
- **ツーリングによる問題解決** が CLAUDE.md の指示よりも効果的

## 考察: upgrade スクリプトと opencode のタスク遂行

### スクリプト使用が「opencode のタスク遂行」と言えるか

v3 後半の高い成功率（全条件達成率 64%）は upgrade スクリプトの導入に大きく依存している。LLM は `bash .claude/scripts/upgrade_to_rails81.sh` を1行実行するだけで Rails アップグレードを完了できた。この事実をどう評価するかについて、複数の視点から整理する。

#### 言える側面

各イテレーションのタスクは「テストカバレッジ向上 + Rails 8.1 アップグレード + リグレッション確認」の3要素で構成されている。スクリプトが担うのはアップグレード部分のみであり、残りの2要素—新規テストの設計・実装とテスト実行・失敗時の修正—は LLM が自律的に遂行している。全条件達成の 12 回では、平均 17.8 個のテストメソッドを追加し、0 failures を達成した。これらはスクリプトでは実現できない LLM の判断と実装能力によるものである。

#### 言えない側面

アップグレード手順自体は LLM が考案・実行しているわけではなく、事前に正解が書かれたスクリプトを呼び出しているだけである。v2 の iter 22 では LLM がスクリプトなしで Docker build から Rails アップグレード、テスト実行までを自力で遂行して全条件達成に成功しており、ローカル LLM でも手順を正しく踏めば達成可能であることが示されている。スクリプトは LLM の能力を補完しているのではなく、LLM が繰り返し失敗する部分を完全に代替している。

#### 実験としての位置づけ

この実験の主目的は「opencode が Rails アップグレードをできるか」ではなく、「CLAUDE.md の累積改善でローカル LLM の成功率をどこまで上げられるか」である。スクリプトの導入は CLAUDE.md 改善の延長線上にある—指示の粒度を「手順の自然言語での説明」から「スクリプト1行の呼び出し指示」に変えたものと捉えることができる。

CLAUDE.md による指示は本質的に「LLM が正しい行動を選択する確率を上げる」メカニズムであり、スクリプトはその極限形態（選択の余地をなくして確率を 100% にする）と言える。「`--no-cache` を付けない」という禁止指示（守られない）と、「このスクリプトを実行せよ」という肯定指示（守られる）の差は、ローカル LLM における指示設計の重要な知見でもある。

#### v2 との公正な比較

v2 では手動手順の自然言語指示、v3 ではスクリプト1行の呼び出し指示と、評価条件が異なる。v3 後半の全条件達成率 64% を v2 の 10% と直接比較する際は、この違いを考慮する必要がある。ただし、v3 前半（スクリプトなし）の達成率が 0% であったことを踏まえると、v2 の 10% すら「たまたま成功した」可能性があり、スクリプトなしのローカル LLM の Docker build 成功率は本質的に低いと考えられる。

## 結論

1. **テスト実行率は v2 の 20% から v3 の 60% に改善**（後半に限れば 82%）
2. **全条件達成率は v2 の 10% から v3 の 47% に改善**（後半に限れば 64%）
3. **成功時の平均所要時間は 34 分**（v2 の 43 分から改善）
4. 最大の転機は **upgrade スクリプトの導入**（iter 29）と **Ruby 3.4.1 への切り替え**（iter 30 後）
5. CLAUDE.md の累積改善は効果的だが、環境問題の直接修正が不可欠
