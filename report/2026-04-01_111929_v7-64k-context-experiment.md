- 日時: 2026-04-01 20:19 JST
- 作成者: Claude

## 前提条件・目的

- 目的: v6 実験（128K コンテキスト）でのパフォーマンス問題を回避しつつ、v5（32K）の compaction による plan_exit ループ問題も解消する中間値の 64K コンテキストでの動作を検証する
- 仮説: 64K コンテキストは 128K より大幅に高速で、32K より compaction が少なく、plan_exit ループを回避できる

## 環境情報

- LLM: Qwen3.5-122B-A10B (Q4_K_M) on t120h-p100 (4x P100 16GB)
- LLM server ctx-size: 65536 (64K, fit mode MoE CPU offload)
- opencode.json: context 65536, output 16384
- opencode ビルド: rolling-truncation-plan-exit
- ベースブランチ: `iter-v7-base` (= `iter-v6-base` + opencode.json context/output 変更)
- プロンプト: v5a（制約セクションなし）
- KV キャッシュ: 816 MiB (4 GPU × 204 MiB, q8_0) — v6 の半分

## 分析

### 1. パフォーマンス: ハングなし

**v6 の致命的問題であったサーバーハングは v7 では発生しなかった。**

64K コンテキストでの KV キャッシュ (816 MiB) は v6 (1632 MiB) の半分であり、attention 計算の負荷が大幅に軽減された。Context が 75-78% (49-51K トークン) に達しても処理は継続し、compaction が発動してコンテキストが縮小された。

### 2. plan_exit: ループなし

**v5 で問題だった plan_exit ループは v7 でも発生しなかった（v6 と同様）。**

ただし、v7 では compaction が 3-4+ 回発生しており、64K は compaction を「排除」するには不十分だった。それでも plan_exit ループが発生しなかった理由:
- Plan フェーズ完了時の Context は 33-39K (51-60%) で、まだ十分な余裕があった
- Compaction は主に Build フェーズ（Docker ビルド + テスト実行）で発生
- Plan フェーズの情報（計画ファイル、制約）は Compaction サマリに含まれ保持された

### 3. Compaction の影響

**64K では compaction が 3-4+ 回発生したが、タスク完遂には影響しなかった。**

v5 (32K) での compaction は ~22回/回で plan_exit ループを引き起こしたが、v7 の compaction は以下の点で異なる:
- 回数が少ない（3-4回 vs ~22回）
- Plan フェーズ完了後に発生（Plan → Build 遷移は正常に完了）
- Build フェーズの長い出力（Docker ログ、テスト結果）が原因で、重要な文脈は Compaction サマリに保持された

### 4. Rails 8.1.3 / Ruby 3.3.0 互換性問題

**両イテレーションで Rails 8.1.3 + Ruby 3.3.0 の互換性問題に遭遇した。**

actionview 8.1.3 が Ruby 3.4+ の無名パラメータ構文（`def capture(*, **, &block)`）を使用しており、Ruby 3.3.0 では構文エラーとなる。

| iter | 対応 | Ruby 最終 | Rails 最終 | 合理性 |
|------|------|----------|-----------|--------|
| 68 | 人間介入で Ruby 3.4 指示 | 3.4.0 | 8.1.3 | 部分的合理（CLAUDE.md 違反だが動作） |
| 69 | 自律的に調査→Ruby 3.4 選択 | 3.4.0 | 8.1.2 | 部分的合理（制約を認識した上で回避策を選択） |

iter 69 は特に注目に値する: LLM は CLAUDE.md の「Ruby 3.3.0 必須」制約を Plan に明記していたにもかかわらず、実際のエラーに直面して自律的に Ruby 3.4 への移行を判断した。さらに Rails 8.1.2 にバージョンを固定し（gem unpack で actionview のソースを調査した上で）、8.1.3 と同じ構文が使われていることを確認するなど、体系的な調査を行った。

## 結論

### 64K コンテキストの評価

| 項目 | 評価 |
|------|------|
| サーバーハングなし | ✓ 成功 |
| plan_exit ループなし | ✓ 成功 |
| タスク完遂 | ✓ 成功 (2/2) |
| パフォーマンス | ✓ 実用的（ハングなし、速度低下も限定的） |
| Compaction なし | ✗ 失敗（3-4+回/イテレーション発生） |

### v4 構成との比較

| 観点 | v7 (64K/64K) | v4 (16K/131K) |
|------|-------------|--------------|
| 成功率 | 2/2 (100%)* | 4/8 (50%) |
| Compaction | 3-4+回/回 | 0 |
| Truncation | 24-34回 | 17-117回 |
| plan_exit | 0% ループ | 0% ループ |
| ハング | 0% | 0% |

*サンプル数が 2 と少ないため、統計的な結論は出せない

### 推奨事項

1. **v7 構成（64K/64K）は実用的**: ハングなし + plan_exit ループなし + 高い成功率
2. **追加イテレーション (70-72) を推奨**: 2 回では統計的有意性が不十分。3 回追加して 5 回中の成功率を評価すべき
3. **Rails 8.1.x + Ruby 3.3.0 の互換性問題は CLAUDE.md の制約修正が必要**: 現状の CLAUDE.md は Ruby 3.3.0 を要求しているが、Rails 8.1.3+ は Ruby 3.4+ を要求する。この制約を更新するか、Rails 8.1.2 以前を固定するかの判断が必要
4. **Compaction は発生するが許容範囲**: Plan → Build 遷移後に発生しており、plan_exit ループには影響していない

### 今後の実験案

- **v7 iter 70-72**: 現在の構成で残り 3 回を実行し、成功率の信頼性を高める
