## 前提条件・目的

- 目的: v7 実験（64K コンテキスト）の iter 68-69（2/2 全条件達成）に続き、統計的信頼性を高めるため +8 回（iter 70-77）を追加実施し、合計 10 回での全条件達成率を評価する
- 仮説: v7 構成（64K/64K）は v4（50%）より高い全条件達成率を示す
- 判定基準: 10 回中の達成率で v4 (50%) との差が統計的に有意かどうか

## 分析

### 1. 成功/失敗パターン

**明確な二分パターンが存在する:**

| パターン | 件数 | Rails 最終 | Ruby 最終 | 全条件 |
|---------|------|-----------|----------|--------|
| Ruby アップグレード | 6 | 8.1.2-8.1.3 | 3.3.1-3.4.0 | **YES** |
| Rails ダウングレード | 4 | 8.0.5 | 3.3.0 | **NO** |

成功した 6 回は全て Ruby を 3.3.1 以上にアップグレードして Rails 8.1.x を維持した。失敗した 4 回は全て Ruby 3.3.0 のまま Rails を 8.0.x にダウングレードした。

### 2. 根本原因: actionview 8.1.x の Ruby 3.3.0 非互換

actionview 8.1.3 の `capture_helper.rb` が Ruby 3.4+ で導入された無名パラメータ構文（`def capture(*, **, &block)`）を使用している。この構文は:

- Ruby 3.3.0: **構文エラー**（SyntaxError）
- Ruby 3.3.1+: **動作する**（バックポートされた修正）
- Ruby 3.4.0+: **正式サポート**

LLM が Ruby 3.3.1+ への更新を発見できたかどうかが成功/失敗を分けた。Rails 8.0.x へのダウングレードは「動作する」が、タスクの条件（Rails 8.1.x）を満たさない。

### 3. plan_exit: 10/10 成功

**全 10 回で plan_exit が正常に動作し、ループは一切発生しなかった。**

v5 (32K) で 2/3 の確率で発生していた plan_exit ループ問題は、64K コンテキストでは完全に解消された。Compaction が 1-4+ 回発生しているにもかかわらず、Plan フェーズ完了時点では十分なコンテキスト余裕があり、plan_exit の文脈が保持された。

### 4. サーバーハング: 0/10

**64K コンテキストではサーバーハングは一切発生しなかった。**

Context ピークは最大 89% (58K, iter 70) に達したが、ハングには至らず Compaction が発動して正常に処理が継続された。v6 (128K) で 1/2 の確率で発生していたハング問題は、64K への縮小で完全に回避された。

### 5. Compaction と Truncation

| 指標 | 範囲 | 平均 |
|------|------|------|
| Compaction | 1-4+ | ~2.3 |
| Truncation | 5-34 | ~23 |
| Context ピーク | 40-89% | ~72% |

Compaction は全イテレーションで発生したが、回数は v5 (~22回) に比べて大幅に少なく (1-4+回)、タスク完遂への悪影響は見られなかった。

### 6. 統計的検定

**帰無仮説 H0: p = 0.5（v4 と同じ成功率）**

- 観測値: x = 6 成功 / n = 10 試行
- 検定: 二項検定（片側、p > 0.5）
- p-value: P(X >= 6 | n=10, p=0.5) = 0.377

**p-value = 0.377 であり、有意水準 0.05 で帰無仮説を棄却できない。**

v7 の全条件達成率 60% は v4 の 50% より高いが、サンプルサイズ n=10 では統計的に有意な差を示すには不十分である。有意水準 5% で片側検定を棄却するには 10 回中 8 回以上の成功が必要だった。

### 7. v4 との実質的比較

統計的有意性は示せなかったが、以下の運用上の優位性がある:

| 観点 | v7 (64K/64K) | v4 (16K+131K) |
|------|-------------|--------------|
| 全条件達成率 | 6/10 (60%) | 4/8 (50%) |
| plan_exit ループ | 0/10 (0%) | 0/8 (0%) |
| サーバーハング | 0/10 (0%) | 0/8 (0%) |
| 構成の単純さ | context=output=64K | server=16K, opencode=131K(不一致) |
| テスト追加 | 9/10 (90%) | 8/8 (100%) |

v4 では server ctx-size (16K) と opencode context (131K) が不一致であり、実質的には 16K で動作していた。v7 は server/opencode ともに 64K で一致しており、構成が単純で再現性が高い。

## 結論

### 64K コンテキスト (v7) の最終評価

| 項目 | 評価 | 詳細 |
|------|------|------|
| サーバーハングなし | **合格** | 0/10、128K (v6) の問題を完全回避 |
| plan_exit ループなし | **合格** | 0/10、32K (v5) の問題を完全回避 |
| タスク完遂率 | **条件付き合格** | 6/10 (60%)、v4 (50%) より高いが統計的に有意ではない |
| パフォーマンス | **合格** | ハングなし、Context 89% でも正常動作 |
| 安定性 | **合格** | 全 10 回で人間介入なしで最後まで到達（iter 68 の 1 回を除く） |

### 成功率の制約要因

全条件達成率 60% の制約要因は opencode/LLM の構成ではなく、**タスク固有の技術的問題**（actionview 8.1.x + Ruby 3.3.0 の非互換）である。失敗した 4 回は全て同じパターン（Rails ダウングレード）であり、LLM がこの特定の互換性問題を発見・解決できるかどうかに依存していた。

### 推奨事項

1. **v7 構成（64K/64K）を現時点でのベスト構成として採用する**: ハングなし + plan_exit ループなし + 60% の全条件達成率。v4/v5/v6 のいずれよりも安定性が高い
2. **統計的有意性の追求には追加実験が必要**: n=10 では p=0.5 との差を示せなかった。有意性を示すには n=20-30 程度が必要だが、1 回 2-4 時間のコストを考慮すると費用対効果が低い
3. **タスクプロンプトの改善を検討**: 失敗パターンが「Ruby 3.3.0 のまま Rails ダウングレード」に集中しているため、CLAUDE.md に Ruby 3.3.1+ への更新を許容する旨のヒントを追加することで成功率を向上できる可能性がある
4. **次の実験軸**: LLM 構成の最適化よりも、プロンプト/CLAUDE.md の改善による成功率向上を優先すべき
