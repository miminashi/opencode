# opencode plan モード stall: ctx-size 96k / 64k 再現実験

- 日時: 2026-05-02 09:30 JST（実験開始 06:32 JST、完了 09:14 JST）
- 作成者: Claude

## 前提条件・目的

[2026-05-02_055422_llm_stall_diagnosis](./2026-05-02_055422_llm_stall_diagnosis.md) で `unsloth/Qwen3.5-122B-A10B-GGUF:Q4_K_M` + ctx=131072 において「真の stall（GPU 0% / 2 分以上 idle / 外部 timeout で abort）」を観測した。同レポートの「短期対策」では `ctx-size 削減: 131072 → 65536` を提案しているが、**実証データはまだ取られていなかった**（v7 メモリの 64K 完走実験は 35B-A3B モデル時代のもの）。

本実験では **同一 prompt / 同一 opencode binary** を保ったまま、llama-server の ctx-size のみを **96k (98304) と 64k (65536)** に切り替えて 5 trial ずつ実行し、131072 (4/5 stall) と直接比較する。

**結論を先に書くと**: 96k で 5/5 stall、64k で 5/5 stall（131072 の 4/5 より悪化）。ただし stall の **発生機序は ctx=131072 とは別物**であることが観測データから判明した。「ctx 削減で stall は減らない」が「stall の中身が変わる」。

## 実験手順

### Step 0: 事前確認

- `/health` で現行 llama-server (ctx=131072) の稼働確認 → idle で OK
- `pgrep -af llama-server` で起動引数を回収
- `gpu-server` lock 状況を確認 → 他者使用なし
- opencode binary・ytdlor 状態確認 → クリーン

### Step 1: 実験基盤の準備

CLAUDE.md のパイプ・リダイレクト禁止ルールに従い、観測は Python で実装：

- [`observe_slots.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/) — `/slots` を 10 秒間隔で JSONL 追記
- [`observe_gpu.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/) — `ssh ... nvidia-smi` を 10 秒間隔で CSV 追記
- [`observe_log.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/) — `ssh ... tail -F` を Popen の stdout=file で書き込み
- [`run_ctx_trials.sh`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/run_ctx_trials.sh) — `run_planenoent_test.sh` をパラメータ化、末尾に `_done.marker` を出力

3 つの観測スクリプトは tmux ウインドウ（slots-watch / gpu-watch / llama-log）で起動、5 trial は opencode-test ウインドウから実行（CLAUDE.md 実行確認ルール遵守）。

### Step 2: 96k 条件 (ctx=98304)

1. `gpu-server lock.sh t120h-p100` 取得
2. 既存 llama-server (131072) を `stop.sh` で停止
3. `start.sh t120h-p100 "unsloth/Qwen3.5-122B-A10B-GGUF:Q4_K_M" fit 98304`
4. `wait-ready.sh` で起動確認（attempt 1/60 で ready）
5. 観測 3 本を tmux で起動 → 出力先 `attachment/.../96k/`
6. `bash run_ctx_trials.sh 96k 5 .../96k` を opencode-test で実行
7. Monitor で trial 完了通知 + `_done.marker` 待機
8. 観測停止 → `stop.sh`

### Step 3: 64k 条件 (ctx=65536)

Step 2 と同手順を ctx=65536 で実行。観測出力は `attachment/.../64k/`。

### Step 4: 元状態への復元

- `start.sh ... fit`（ctx=131072）→ `wait-ready.sh` → `unlock.sh`
- 復元後 `/slots` で `n_ctx=131072` を確認

### 結果 5: 96k trial-3 の異常 — plan mode で AGENTS.md が編集された

96k trial-3 は `plan_exit_calls=0` かつ `rc=124` でありながら `result=MODIFIED`（AGENTS.md の内容が変化）。tool_uses を見ると `edit` が 1 回呼ばれている。これは **plan mode 中に build agent の `edit` tool が（subagent または直接経路で）呼ばれた**ことを示しており、`fix-plan-subagent-readonly` ワークツリーが目指している「plan mode の subagent から書き込みを許さない」修正がこの trial では機能していない可能性がある（別タスクで追加調査）。

### 結果 6: 判定マトリクスへの当てはめ（96k / 64k vs 131072）

[2026-05-02_055422 診断レポート](./2026-05-02_055422_llm_stall_diagnosis.md) の判定マトリクス：

| 観測 | 131072 結果 | 96k / 64k 結果 | 仮説への影響 |
|---|---|---|---|
| GPU 使用率 | 0% × 4 GPU、power 40-50W (idle) | **97-98% で常時稼働、最長 idle 28s/11s** | 131072=A支持 / **96k,64k=A否定** |
| `n_decoded` 増分 | stall 中は 0 | 継続的に増加 | 131072=A支持 / **96k,64k=B も否定（生成中だから「遅い」ではなく別問題）** |
| llama-server log 末尾 | `cancel task`（外部 abort） | `cancel task` も多発（trial 区切り時） | どちらも timeout 起源だが意味は別 |
| reasoning chunk 受信 | 全て届いている | 全て届いている | C 否定（変わらず） |
| eval rate | 16.7 t/s（正常） | 16.5-17.7 t/s（正常） | B 否定 |
| **`plan_exit` tool_use 発火** | trial-4 のみ 1 回 / trial-1,2,3,5 0 回 | **5+5=10 trial で 0 回** | **新仮説 E: tool selection bias** |

131072 は「真の停止 (A: GPU/llama-server hang)」、96k / 64k は「**plan_exit が選ばれない（仮説 E）**」という別の故障モード。

## 結論

### 1. ctx 削減仮説（[診断レポートの短期対策](./2026-05-02_055422_llm_stall_diagnosis.md#短期実用回避策)）は **棄却**

> 「ctx-size 削減: 131072 → 65536（v7 構成）」で stall は減るはず

**実測**: 131072 (4/5) → 96k (5/5) → 64k (5/5)。stall 率は **悪化**。

### 2. 故障モードは ctx-size で変化する

| ctx | 故障モード | 観測指標 |
|---|---|---|
| 131072 | **A: GPU/llama-server 真の停止** | GPU 0% × 4 が 2 分以上、llama-server で `cancel task` 強制終了 |
| 96k / 64k | **E: モデルが `plan_exit` を選ばない** | GPU 97-98% 稼働、reasoning は「plan_exit を呼ぶべき」と言うが tool_use は出ない |

131072 では「真の hang」、96k/64k では「**LLM が止まらず無限に reasoning と他ツールを生成し続ける**」モードに変わる。両方とも 900s timeout で死ぬので外見は同じ「rc=124」だが、**根本原因は別物**。

### 3. v7 メモリ「64K で 2/2 完走」は現行 122B モデルでは成立しない

メモリの v7 結果は 35B-A3B モデル時代の話。**122B-A10B では 64K でも 0/5 完走**。メモリを更新する必要あり。

### 4. 122B-A10B の `plan_exit` 選定確率が極端に低い

10 trial 中 0 回。一方で `webfetch` / `read` / `write` / `edit` / `task` は適切に選ばれる。これは llama-server のサンプラー設定（`--temp 0.6 --top-p 0.95 --top-k 20`）と組み合わせて、**`plan_exit` トークン列のロジット品質が他ツール名より弱い**可能性を示唆する。

## 対策の方向性（更新）

### 短期（次の trial で試せるもの）

1. **`plan_exit` の reminder を強化**: 現状の「plan_exit reminder」は 64k trial-4 で 1 回しか発火していない。reasoning 末尾に「plan_exit を呼ぶべき」と書いた瞬間に system reminder で push する仕組みを実装
2. **opencode 側 stop-when 条件**: reasoning 末尾文に `plan_exit` キーワードが N 回連続で出ていれば、強制的に `plan_exit` を疑似発火する safeguard（[`packages/opencode/src/session/llm.ts`](../packages/opencode/src/session/llm.ts) の onStepFinish フック）
3. **モデル切替**: Qwen3.5-35B-A3B-GGUF（thinking 対応、より小規模）に戻すと plan_exit 選定が改善する可能性（v7 メモリの過去データが示唆）

### 中期（観測の深掘り）

1. **logits 観測**: llama-server の `--show-logits` (もし対応していれば) または `/v1/completions logprobs` で、reasoning 末尾の段階で `plan_exit` トークンに対するモデル確率を直接測定
2. **tool list の順序**: 現状の system prompt で `plan_exit` がツールリストのどの位置にあるか確認、先頭に近づけて attention bias を変える検証
3. **96k trial-3 の MODIFIED 異常**: subagent の edit 呼び出し経路を opencode log で追跡（`fix-plan-subagent-readonly` の修正が機能していないケースの再現）

### 長期（plan mode UX）

1. **plan_exit reminder の system message 注入**: ユーザ tool reminder ではなく LLM 内部の chat completion API が直接受け取る system message として、reasoning 末尾で確定文字列を強制
2. **plan-exit-via-summary 経路**: モデルが plan_exit を選ばなくても reasoning 内容から plan ファイルが生成されていて kill-on-marker できる仕組み

## 注意点・追加調査の必要性

- 各 trial で長時間動作したため、観測サンプルがやや疎（トータル 2.5 時間 × 10 秒間隔 = 約 900 サンプル）。**より細かい時系列で reasoning_delta タイミング × GPU util × tool_use 発火位置**を結合解析する別タスクが望ましい
- 64k trial-4 が 9 step 進行（他は 3-5）した理由は不明（reasoning に `plan_exit reminder` が 1 回入った関係？）
- 96k trial-3 の `result=MODIFIED` は `fix-plan-subagent-readonly` 修正の有効性に直接関係する観測。**別レポートで edit 経路を追跡**すべき
- llama.cpp がビルド更新（96k 起動時に b8993 → b97ebdc98 へ）された影響は理屈上は無視できる範囲（生成ロジックではなく Vulkan/Hexagon 周りの差分）だが、念のため記録

## 再現方法

1. gpu-server lock 取得: `lock.sh t120h-p100`
2. 既存 llama-server を停止: `stop.sh t120h-p100`
3. 各条件の起動:
   - 96k: `start.sh t120h-p100 "unsloth/Qwen3.5-122B-A10B-GGUF:Q4_K_M" fit 98304` → `wait-ready.sh ...`
   - 64k: 同上で `fit 65536`
4. 観測スクリプト 3 本を tmux で起動（[`observe_slots.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/), [`observe_gpu.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/), [`observe_log.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/)）
5. opencode-test tmux で `bash run_ctx_trials.sh 96k 5 <log_dir>`
6. `_done.marker` 出現で次条件へ
7. 全 trial 完了後 `start.sh ... fit` で 131072 復元 → `unlock.sh`

集計スクリプト（観測ログから idle 期間 / tool 内訳を抽出）:

- [`analyze_idle.py`](./attachment/2026-05-02_063235_llm_stall_ctx96k_64k/) — GPU 0% 連続期間
