### 学んだこと

- **bun のバージョン要求は build 開始時にハードチェックされる**: `packages/script/src/index.ts` が `rootPkg.packageManager` の `bun@X.Y.Z` を `^X.Y.Z` で `semver.satisfies` 検証する。upstream が bun を上げると build が即失敗するため、merge-upstream の流れに「bun --version 確認 → 必要なら `bun upgrade`」を組み込むべき。`bun upgrade` は `/home/ubuntu/.bun/bin/bun` をその場で 1.3.14 に置き換えるので、PATH 設定の変更は不要だった。
- **README.md の stash → fast-forward → pop パターン**: 今回のように main dev 側に未コミットの README.md ローカル変更がある状態で upstream も README.md を変更している場合、`git merge --ff-only` は overwrite を防ぐために失敗する。`git stash push -- README.md`（特定ファイルだけ stash）→ `git merge --ff-only` → `git stash pop`（auto-merge）で安全に解決できる。fork の "LLM サーバの起動" セクションは line 59 付近、upstream の FAQ 削除は line 186 付近で離れているため、3-way merge は完全自動。
- **コンフリクトなしマージの所要時間は短い**: merge-upstream-17 が 11 ファイルコンフリクトで多大な手作業を要したのに対し、今回は LLM 応答以外の手作業はほぼゼロ。コンフリクトの有無は upstream 側の変更の "fork が触っている領域への接近度" に強く依存し、今回は Effect 化や RuntimeFlags のような大規模リファクタが谷間に入った時期だったため fork 側の差分とほぼ衝突しなかった。
- **upstream が dialog-prompt submit keybind を 1 リリースで add → revert → add し直している**: `d441e931f (add) → cc9c0b15c (revert) → f97e115ee (re-add)`。短いウインドウで挙動が二転三転するので、fork のキーバインド関連の変更には影響しないか後追い確認が必要（今回 fork は dialog-prompt を触っていないため影響なし）。
