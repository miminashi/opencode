## 前提条件・目的

opencode の既定 LLM サーバ運用モデル `unsloth/Qwen3.5-122B-A10B-GGUF:Q4_K_M`（fit プロファイル、t120h-p100、4×P100、eval ~17 t/s）の **置き換え候補**として、新規追加された Qwen3.6 系 4 モデル（27B dense / 35B-A3B MoE / 各 MTP 版）の **速度** と **賢さ** を実コーディングワークロードで評価する。判定が肯定的な場合、opencode の既定モデルを切り替える。

- 過去のベンチ（`report/2026-05-02_063235_llm_stall_ctx96k_64k.md` 等）は合成プロンプト寄り → 今回は実コーディング負荷で評価
- ベンチターゲット: `ytdlor` プロジェクト（Rails 8.1.2 / PostgreSQL 14 / Hotwire、main HEAD `3ac3acd`）
- 評価軸: 自動指標（rails test 通過、ビルド成功、diff の有無/サイズ）+ LLM-as-judge（Claude Code の Agent 並列で実施、本レポートに反映済み）

## 既知の落とし穴と対処

以下は本ベンチで実際に踏んだ問題と回避方法。**回避手順は run_trial.sh / run_benchmark.sh に組み込み済み**だが、別環境再現時の前提知識として明記する。

### 1. opencode の SQLite 共有 DB 競合 (致命的)

- **症状**: 各 trial の opencode が起動 2-3 秒で rc=1 で死ぬ。stderr に `Failed to run the query 'CREATE TABLE project ...'` (CREATE TABLE 衝突)
- **原因**: opencode は `~/.local/share/opencode/db.sqlite` を全プロセス共有。worktree 切替で各 trial が「新規 project」として CREATE TABLE を試み衝突
- **回避**: `run_trial.sh` で `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` を trial 専用ディレクトリ (`$TRIAL_DIR/.xdg_*`) に export する
- **検証**: trial dir に `.xdg_data/opencode/opencode.db` が独立して作られていれば OK

### 2. Ruby version mismatch (致命的)

- **症状**: `./docker_compose run --rm web bin/rails ...` が `Your Ruby version is 3.2.4, but your Gemfile specified 3.3.7 (Bundler::RubyVersionMismatch)` で死ぬ
- **原因**: 既存の `ytdlor:latest` docker image が古い Ruby 3.2.4 ベース、最新 Gemfile が 3.3.7 を要求
- **回避**: 事前に `./docker_compose --profile test build web worker test` で再ビルド

### 3. Rails 8 minitest 出力形式

- **症状**: `collect_metrics.py` の `TEST_SUMMARY_RE` で `(\d+)\s+tests?` を要求していたため、Rails 8 の `"8 runs, 9 assertions, ..."` を捕捉できず、`test_count=null` で `test_passed=False` 誤判定が連発
- **回避**: 正規表現を `(\d+)\s+(?:tests?|runs?)` に拡張（修正済み）

### 4. q36-27b dense + 131072 ctx で CUDA OOM

- **症状**: llama-server が `CUDA error: out of memory (current device: 3)` で abort、以降の opencode は接続不能
- **原因**: dense 27B + 131072 ctx の KV cache が P100×4 (64GB) では不足
- **回避**: q36-27b では ctx を 65536 程度に下げる、または fit プロファイルを適用（27B 用は未実装）
- **本ベンチでは**: q36-27b は OOM 確定として記録、運用候補から除外

### 5. ytdlor の docker_compose は cwd 依存

- `./docker_compose` スクリプトが `secret.txt` / `default_secret.txt` を **cwd 基準で探す**
- `bash /full/path/to/docker_compose` だと cwd がベンチホストの opencode dir のままで secret が見つからない
- `run_trial.sh` 内で `cd "$WORKTREE_DIR"` 後に `./docker_compose ...` を呼ぶ（実装済み）

### 6. q35-122b の M タスクで 1500s タイムアウト

- **症状**: q35-122b 単独で M タスク 3/3 timeout (rc=124, wall_time=1500s)
- **原因**: 122B + 実コーディング負荷で 25 分予算では完走不可
- **回避策の選択肢**:
  - timeout を 30-45 分に延長（ただし他モデルとの公平比較に影響）
  - 本ベンチでは「timeout も結果の一部」として採用、judge スコアでばらつきを評価

### 7. db/schema.rb の大量 diff

- **症状**: 全 trial の `worktree_diff.patch` に `db/schema.rb` の 50-90 行の差分
- **原因**: ベースコミット時の schema.rb は Rails 7.1 形式、`db:migrate RAILS_ENV=test` で 8.1 形式に正規化 (カラム順アルファベット化、`pg_catalog.plpgsql` 表記等)
- **影響**: LLM の責任ではない自動変更だが、`diff_lines_added` を膨らませる
- **対処**: judge agent には「schema.rb 差分は採点に含めない」と指示済み。`collect_metrics.py` の `diff_lines_added` は ノイズ込みである点に注意

## ベンチマーク設計

### タスク（3 段階、全モデル同一プロンプト）

- **S（小、~30 行）**: `Archive` モデルに `original_url` のフォーマットバリデーション（URI::HTTP/HTTPS）+ モデルテスト 3 件追加
- **M（中、~80 行）**: `Archive` に `:completed` / `:pending` scope 追加 + `ArchivesController#index` に `?filter=` 分岐 + テスト 4 件追加
- **L（大、~250 行）**: `Tag` モデル新規追加（migration、`has_many :tags through:`、`TagsController` index/show、ビュー、テスト一式）

### 実行方法

- 各 `(モデル × タスク)` を 3 回繰り返し（45 trial）
- 各 trial は独立 worktree (`bench-<short>-<task>-r<n>`)、共通ベースコミット `3ac3acd`
- 1 trial の制限時間: opencode 1500s（25min）、rails test 600s
- 1 モデルの予算: q35-122b は 10800s、q36-35b は 9000s、他は 5400-7200s
- 全体予算: 12h（実消費 7h4min）

### 評価指標

- `wall_time_s`: opencode 起動から終了までの実時間
- `eval_tps_approx`: `tokens_output / wall_time_s`（実効スループット）
- `auto_score`: `diff_exists + build_ok + test_passed`（最大 3）
- `test_passed`: 緩和判定（既存ネットワーク依存テスト 3 件失敗まで許容、`failures <= 3 and errors == 0`）
- `llm_judge_score`: Claude Opus 4.7 による 1-5 採点（実施済み、Claude Code の Agent 並列方式 = 「方法 B」）。詳細は「再現方法 → LLM-as-judge を実行する場合」参照

## モデル別詳細

### q36-35b (dense 35B-A3B MoE) — **置換最有力候補**

- 全 9 trial で完走、test_pass 9/9
- eval_tps 12.0（**122B の 4.0 倍**）
- L で diff 191 行、wall 482s（122B 比 **2.1 倍速** + 同等品質）
- 安定性 ◎、tool_use 平均 23.4 回（最多）— エージェント的に活発

### q36-35b-mtp (dense 35B-A3B + MTP) — 次点

- 全 9 trial 完走、test_pass 8/9（L で 1 件失敗）
- eval_tps 8.3（122B の 2.8 倍）
- **MTP は非 MTP より遅い結果**（後述、所見）
- L で diff 176 行（やや少ない）

### q36-27b-mtp (dense 27B + MTP) — 速度不足

- S/M は完走、**L 3 trial 全て budget_exhausted で skip**
- S 461s, M 1089s、9 trial で 5400s 予算を S/M で食い切り L 不可
- MTP オーバーヘッド + dense 27B の重さで実用速度を満たさず

### q36-27b (dense 27B、非 MTP) — **CUDA OOM で運用不可**

- llama-server.log に `CUDA error: out of memory (current device: 3)` → llama-server クラッシュ
- 131072 ctx + dense 27B + P100×4 (64GB) で KV cache が VRAM 不足
- **全 9 trial で opencode は LLM 接続不能で即死**（step_count=0, tokens=null, 「Unable to connect」エラーのみ）。S r1 の wall_time 282s は実は DB 初期化時間で、opencode 本体は他 trial 同様即死だった（judge agent の精査により判明）
- diff_lines_added 46 は **bench スクリプトが auto reset した `db/schema.rb` の正規化のみ**（Rails 7.1 → 8.1 形式更新、カラム順、`pg_catalog.plpgsql` 表記）。LLM による実装作業は皆無。
- judge_score 1.0（全 trial）
- 解決には ctx 削減（例: 65536）or fit プロファイル適用が必要

### q35-122b (現行運用モデル) — M が致命的に遅い

- S: 3/3 完走、平均 626s
- **M: 3/3 timeout (1500s 上限)** — read/edit 多用フェーズでステップ数が爆発
- L: 3/3 完走（diff 190 行、test pass）、平均 1016s
- 速度は他モデルの 1/3 以下、現行運用上で **M タスクが完走不能**

## 故障モード

### A: CUDA OOM (q36-27b dense)

- 131072 ctx 確保 + dense 27B + P100×4 (64GB)
- KV cache が GPU 3 で枯渇、`alloc at /home/llm/llama.cpp/ggml/src/ggml-cuda/ggml-cuda.cu:527` で abort
- **全 9 trial で opencode が「Unable to connect」即死**（llama-server クラッシュ後の connect 失敗）。S r1 の wall_time 282s は DB 初期化時間で、opencode 本体は即死していた点に注意（judge agent 精査で判明）
- 影響: **q36-27b は現状の運用条件（131072 ctx）では使用不可**

### B: opencode timeout (q35-122b M タスク 3/3)

- 1500s 上限到達、`opencode_rc=124`
- M タスク特有: 既存 Archive モデル拡張 + コントローラ修正 → read/edit 多用 → ステップ数増 → 完走不可
- L は新規ファイル作成中心で 1000s で完走可能

### C: budget_exhausted (q36-27b-mtp L 3/3 skip)

- 個別モデル予算 5400s に対し、S+M で 4650s 消費、残り 13min で L 3 trial 不可
- skip 判定で `trial.json` に `{"skipped":true,"reason":"budget_exhausted"}` 記録

### 🏆 最終結論

**`q36-35b` (`unsloth/Qwen3.6-35B-A3B-GGUF:UD-Q4_K_XL`、dense 35B A3B activated MoE、UD-Q4_K_XL) を q35-122b の置換として推奨。**

確定理由:
1. **judge_score 4.44 で全モデル中最高**（q35-122b 3.89 を +0.55 上回る）
2. **wall_time が 122B の 1/3 以下**（365s vs 1047s = ×2.9 速い）
3. **L タスク（最大難度）で q35-122b と並ぶ judge 4.67**（同等品質）
4. **唯一 9/9 全完走したモデル**（最高の安定性）
5. **eval_tps 12.0 で 122B の 4 倍**（L で 16 t/s ピーク）

## その他の所見

### MTP は実効スループットで逆効果

| モデル | eval_tps (全体) |
|--------|--------:|
| q36-35b（非 MTP） | **12.0** |
| q36-35b-mtp（MTP） | 8.3 |

dense 27B でも q36-27b は OOM のため直接比較不可だが、q36-27b-mtp の eval_tps 4.3 も期待外れ。

**仮説**: opencode のような **tool-heavy workload** では、生成途中に tool 呼び出しが入って prompt が再構築されるため、speculative decoding の draft が無効化される率が高い。MTP overhead（draft heads の inference）だけが残る形に。

→ ベンチ系（純粋生成）では MTP 効果が出るが、エージェント系では非 MTP 推奨。

### dense 27B + 131072 ctx は P100×4 では VRAM 不足

q36-27b の OOM は **モデル容量 + 131072 ctx の KV cache** が原因。fit プロファイルを 27B にも適用するか、ctx を 65536 に削減すれば運用可能と推定（要追加検証）。

q36-35b（A3B MoE）は active params が 3B なので KV cache が小さく、131072 ctx でも問題なし。

### opencode ベンチ系の故障モード追加 (本ベンチで新規確認)

- **SQLite 共有 DB 競合**: `~/.local/share/opencode/db.sqlite` は全 opencode プロセス共有。worktree 切替で各 trial が「新規 project」として `CREATE TABLE` を試み、衝突 → opencode rc=1 即死。**XDG_DATA_HOME を trial ごとに分離**することで回避。
- **Docker image の Ruby version mismatch**: 既存 image が古い Ruby 3.2.4、最新 Gemfile が 3.3.7 を要求。`docker_compose build` で再ビルドが必要。
- **Rails 8 minitest 出力形式**: `"8 tests"` → `"8 runs"` に変更。collect_metrics の正規表現修正で対応。

1. ユーザーから「judge を方法 B で実行」と依頼を受ける

- `correctness`: 要件への適合度
- `idiomaticity`: Rails らしさ

- 総合 `score` (1-5)

出力フォーマット（各 trial dir に judge.json):

```json
    "correctness": 4,
    "idiomaticity": 5,
    "completeness": 4,
    "test_quality": 4
  },

}
```


- prompt caching が効きにくい（各 Agent が独立 invocation）
- 採点モデルは Claude Code が使う Claude Opus のバージョンに依存（本ベンチは Opus 4.7 想定）
- 同じ prompt でも temperature による出力の揺れあり。完全な数値再現を求める場合は `judge.py` 方式（Anthropic SDK 直接）を推奨
