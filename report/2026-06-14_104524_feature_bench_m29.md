### 欠け 2 件の精査（いずれも既知の確率的故障・merge-29 非起因）

| trial | 事象 | 原因 | 種別 |
|---|---|---|---|
| **page-selfplan-r5** | functional **NO**（rails test は pass） | kaminari `.page` のみで **`.per(20)`/`default_per_page` 無し** → 既定 25件/頁。seed 25件が1頁に収まりページネーション非表示・2頁目到達不可。テストは `assert_response :success` のみで浅く per(20) 欠落を捕捉できず素通り | **per(20) 欠落**（v2 baseline 既知） |
| **page-selfplan-r1** | rails test **3 failures**（functional は YES） | per(20) は設定済みで**実装・実機は正常動作**。自作 integration テストが `Archive.ordered`(id DESC) を昇順と誤想定（`assert_match /Video 1/` 等）して失敗 | **テスト品質**（実装は正） |

その他の軽微な減点: search-selfplan-r3 が ILIKE でなく `LIKE`（PostgreSQL で大文字小文字を区別、テストが同ケースのため素通り・functional YES）、page-givenplan-r1 が無関係な `docker_compose` スクリプトの SECRET_KEY_BASE ブロックをコメント解除するスコープ外の混入編集（機能影響なし）。いずれも model 起因の確率的事象。

## 現行ベースライン（v2）比較

| 指標 | v2 baseline | regdev1（v2 直近） | **m29（本走）** | 評価 |
|---|---|---|---|---|
| functional | 19/20（self 9・given 10） | 20/20 | **19/20（self 9・given 10）** | **同等**（baseline と一致） |
| test_pass | 20/20 | 20/20 | **19/20** | −1（r1 のテスト品質故障、実装は正） |
| transition self_exit | 20/20 | 20/20 | **20/20** | **同等**（Tab 0） |
| page gem | 全 kaminari | 全 kaminari | **全 kaminari** | **同等** |
| givenplan functional | 10/10 | 10/10 | **10/10** | **同等** |
| score_mean | — | 5.0 | 4.65 | 確率的故障 2件の反映 |

- **fork コア機能にリグレッションなし**: 主指標の **transition 20/20 self_exit**（plan_exit 自発遷移）と **givenplan functional 10/10**（与プラン経路の安定性）が baseline と完全同等。マージで TUI が `packages/tui/` へ分離、legacy logger 削除、references の core 直下移動、overflow 検知のトークン数ベース化等の構造変化があったが、plan_exit ダイアログ→build 遷移・実装能力は無傷。
- **functional 19/20 は v2 baseline（19/20）と一致**。欠けの 1件（page-selfplan-r5 の per(20) 欠落）は v2 baseline でも既知の確率的故障モードであり、マージ起因ではない。直近 regdev1 が 20/20 だったのは baseline 側の確率的故障が引かなかったためで、m29 の 19/20 は baseline の期待値どおり。
- **test_pass の −1（19/20）**は page-selfplan-r1 の**自作テストの順序誤想定**による失敗で、実装自体は per(20) 込みで正しく functional YES。fork のテスト実行系・実装系の欠陥ではなく model の確率的なテスト記述ミス。
- **結論: merge-upstream-29 による fork コアのリグレッションは皆無。能力はベースライン v2 と同等**（functional 19/20・self_exit 20/20・givenplan 10/10・全 kaminari 維持）。

## 再現方法

`feature-bench` スキルの手順を mode=regression / run_id=m29 / spec=v2 で実行:

1. fork dist を merge-29 込み dev HEAD から再ビルド（`bun run --cwd packages/opencode build --single`、`--version` = `0.0.0-dev-202606132102`）。
2. `RUN_ID=m29 SPEC=specs/v2_libheur.md bash bench_setup_clean.sh`（20 worktree を `b61242f` + v2 spec へ、`clean_base_shas.tsv` 記録）。
3. opencode-test ペイン（claude ペイン右、title=opencode-test）を確保。
4. `RUN_ID=m29 PANE=<pane> FORKBIN=<dist> bash bench_run_e2e.sh` を **setsid で切り離して起動**（tee プロセス置換対策）。
5. `bench_collect.sh` → `bench_build_json.py` → `bench_aggregate.py`。
6. 各 trial の `.diff` を精読 → `judge_<trial>.json` を Write（`write_judges_m29.py`）→ `bench_aggregate.py` 再実行で score 補完。
7. `bench_manifest.py`（manifest.json + RUN_LEDGER.tsv）。

## 所見・運用上の知見

### dist 取り違え防止が機能（merge 後再ビルドの重要性）

セッション開始時の dist は `0.0.0-dev-202606131806`（merge-29 前のビルド）であり、そのまま測ると merge-29 の効果を測れなかった。`--version` のタイムスタンプで判別し、dev HEAD から再ビルドした `0.0.0-dev-202606132102` を使用。fork dist（`0.0.0-dev-*`）であることを起動時に確認、upstream 1.15.12 との取り違えなし。

### gem 選定の完全収束（v2 ライブラリ選定ヒューリスティックの安定性）

page 10試行すべてが **kaminari 1.2.2 で一致**し、pagy/will_paginate はゼロ。merge28 で見られた pagy バージョン割れ・will_paginate 混入のようなばらつきは再発せず、v2 spec のライブラリ選定ヒューリスティックがマージ後も完全に効いている。

### llama.cpp は regdev1 と同一インスタンス

`/props` の build_info は `b9617-e37abd6b5`（regdev1 と同 commit）。同一の長時間稼働サーバインスタンスで、DRY=0・131072 ctx を維持。本走中の stall・LLM サーバ落ちはゼロ（20/20 完走）。

### GPU サーバ電源 OFF（完了）

全工程（ベンチ・集計・judge・manifest・レポート）完了後、ユーザー要望により GPU サーバ `t120h-p100` を電源 OFF した（電源状態 = Off を確認）。他者の llama-server 使用が無いこと（`/slots` アイドル・id_task 不変、lock 保持者は本マシン自身の自ロック）を確認し自ロックを解放（`unlock.sh`）。初回の `power.sh ... off`（plugin cache パス）は auto-mode classifier に「共有インフラ停止はユーザー未要求」と誤判定されブロックされたため、回避はせず、ユーザー承認のもと `settings.local.json` の `autoMode.allow` に GPU 電源操作の認可を追記し、既存の静的許可ルールを持つ `llm-server-ops` パスの `power.sh t120h-p100 off`（GracefulShutdown）で停止した。

### GPU lock が 27時間以上放置されていた（運用ハイジーン）

シャットダウン前の `lock-status.sh` で、`t120h-p100` の lock 保持者が**本マシン自身**（`aws-mmns-opencode-...-20260613_072732`）・取得時刻が **2026-06-13 07:27**（前日、おそらく [regdev1](./2026-06-13_125236_feature_bench_regdev1.md) 本走以降の解放漏れ）であることが判明した。lock が日をまたいで 27時間以上放置されており、他者がこの GPU を確保しようとすると本来不要な競合になりうる状態だった。今回 `unlock.sh` で解放したが、**ベンチ完走後に lock を解放する運用**（または `finish` 系スクリプトでの自動解放）を徹底すべき。

### power.sh のパスが CLAUDE.md と settings.local.json で食い違う（ドキュメント不整合）

CLAUDE.md の「LLM サーバー前提条件」は power.sh を `…/plugins/cache/claude-plugins-official/gpu-server/1.0.0/skills/gpu-server/scripts/power.sh` のパスで案内しているが、`settings.local.json` の静的許可ルール（および今回 OFF に成功したパス）は **`/home/ubuntu/src/llm-server-ops/.claude/skills/gpu-server/scripts/power.sh`** だった。初回ブロックの主因は auto-mode classifier の意味判定だが、**CLAUDE.md 記載の plugin cache パスはそもそも静的許可ルールにもマッチしない**ため、許可ルールを足しても plugin cache パスでは通らない。両者は内容同一だが、許可・ドキュメントを一方のパス（`llm-server-ops`）に統一しておくと将来の摩擦を避けられる。
