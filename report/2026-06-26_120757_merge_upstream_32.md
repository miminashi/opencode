### 初回コンフリクト解消の誤判断と learning

3 ファイルで初回判断を誤り、ビルド/typecheck が指摘するまで気付かなかった。次回マージで同じ罠を避けるための学び:

- **v1/session.ts (重大)**: コンフリクトマーカーは `<<<<<<< HEAD` 行 68 / `=======` 行 654 / `>>>>>>> upstream/dev` 行 656 で、HEAD ブロックは行 69-653 (約 585 行) / upstream ブロックは行 655 (1 行) と非対称。HEAD ブロック全体をそのまま残す形で解消したが、これが間違い。upstream は v1 schema を `packages/schema/src/v1/session.ts` に分離して 1-46 行に大量の `export { ... } from "@opencode-ai/schema/session-v1"` を追加しており、HEAD ブロック内の旧定義群と全衝突した。結果 `Multiple exports with the same name "Assistant"/"Info"/"WithParts"/"SessionInfo"/"Event"` 5 件のビルドエラー。教訓: **HEAD ブロックが「巨大な class/Schema/Event 定義の集合」で upstream が「短い re-export」の場合、HEAD ブロックは upstream の別 package への移動で重複している可能性を疑え**。fork 独自追加 (StallTimeoutError 等) と upstream で別 package へ移動した定義を切り分ける必要がある (前者は core 側ローカル定義として保持、後者は削除)。
- **registry.ts (中程度)**: upstream の `LayerNode.make({...})` 新シグネチャ + `deps` から Permission/SessionCompaction.node 除去を見て同調したが、typecheck で `Missing dependencies` エラー。upstream で外せている理由は未調査 (おそらく他経路で provide) だが、**fork 側では deps に戻さないと型解決できない**。教訓: **upstream で deps を外す動きを見ても、fork コード全体で他経路 provide が確認できなければ盲信せず復元する**。
- **help-snapshots.test.ts.snap (軽微)**: fork の `--interactive`/`--replay` 系オプションは builder からは消えている (auto-merge で削除) のに snap には残してしまうところだったが、レビュー時に「ビルド側に option 定義がない → help にも出ないはず」と気づいて snap 側を upstream 寄せに修正した。

## 次回マージ前提の構造変化

- **`LayerNode.make({ service, layer, deps })` 新シグネチャ必須**: 旧 `(layer, [deps])` 形は型エラー。`Service` 引数の明示が必要。fork が独自 service の `.node` export を追加する際は 3 引数オブジェクト形で記述
- **v1 schema が `@opencode-ai/schema/session-v1` 経由**: fork が v1 型 (CompactionPart の field 追加 / AssistantErrorSchema の Union 拡張など) を変えたい場合、`packages/schema/src/v1/session.ts` 側に直接手を入れる。`packages/core/src/v1/session.ts` は upstream で 68 行に縮小 (re-export 中心 + NamedError ローカル定義のみ)、fork は `StallTimeoutError` ローカル定義 1 ブロックを追加して 74 行
- **`packages/core/src/public/*.ts` 系は削除済**: 古い import (`@opencode-ai/core/public/...`) が混入していたら削除・整理
- **`bun install` をワークツリー単位だけでなくメインリポジトリでも実行**: workspace パッケージが追加された場合、ff で更新された `bun.lock` が反映されても、メインの `node_modules` に workspace シンボリックリンクが張られていないため、新パッケージの import が `Rollup failed to resolve` で失敗する。ff 後の dev ビルドで `Rollup failed to resolve import` が出たら `bun install --cwd /home/ubuntu/projects/opencode` を実行 (lockfile 差分が無くても `node_modules` の workspace リンクが再生成されて解消)
- **CLI `--mini` 追加 (#33353)**: fork wrapper (run.ts handler 内 mini 呼出箇所) で `thinking: undefined` を渡すと TS2322 → `true` で渡す

### コンフリクト解消の罠 (今回獲得)

- **「巨大な HEAD ブロック × 短い upstream re-export」パターンは package 移動を疑う**: HEAD ブロックを保持する判断は危険。upstream で全部 `packages/schema/...` 等に移されている可能性が高い。fork 独自追加と upstream 削除を切り分けて移植する。比較は `git show upstream/dev:<path> | wc -l` で upstream のサイズが急に小さくなっていないか確認するのが早い
- **upstream の deps 削除を盲信しない**: `LayerNode.make` の deps から特定の `.node` が外されていても、fork 側で他経路 provide が確認できなければ復元する。typecheck の `Missing dependencies` で必ず検出されるので、まずは upstream 通りで build → 失敗したら復元、の手順が安全
