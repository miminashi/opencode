## 概要

上流の変更を取り込んだ後、fork 側の実装能力に劣化がないかを確認するため、機能追加ベンチのフルセットを走らせた。結果として基本指標はすべて過去のベースラインと同水準で、隔離監査も全試行が親リポジトリに触れていないことを実証した。上流取り込みが fork の実装能力に影響を与えていないと判断でき、dev ブランチの更新を続ける材料が揃った。

もう一つの目的は、前セッションで新規導入した過剰実装機械指標のベースライン化判断だった。今回の run が試走に続く 2 回目にあたり、事前に定めた 2 回合算の統計基準と 2 つの追加基準（提示プランに従わせた側で不要な差分が発生しないこと、および試走で観測された突出値が単発の外れ値だったのか）を検証した。いずれも成立したため、この指標を正式なベースラインとして登録した。

副次的な観察として、試走で一度だけ登場した別 gem や、実装ゼロ・部分実装の疑い試行はいずれも今回は再現せず、単一 run の LLM の揺らぎだったことが 2 回合算で確認できた。一方で disk 系の selfplan は既知の難しさ由来の失敗パターンが今回も同水準で残っており、これは上流取り込みとは無関係の継続観察項目として扱う。

judge の主観採点は今回 skip した。無回帰判定に必要な基本指標はすべて自動集計で確認できており、単一 run で改善を主張しない運用原則にも合致するため、実用上不要と判断したもの。必要になれば保持した diff から後日遡及して採点できる仕組みがある。

所要時間は試走と同水準で、全試行が完走した。ベンチ集計と隔離監査の完了を確認したうえで、GPU サーバは他利用者の使用がないことを確かめてからシャットダウンした。

## 結果・所見

### 結論

- **upstream/dev 139 コミット取り込み後の fork 実装能力に回帰なし**。既存 CORE HEALTH / CAPABILITY / hallucination / isolation_break で PASS 35 / WATCH 1 / FAIL 0
- **親アクセス監査 35/35 no_parent_access** で隔離修復が 3 run 連続 (合計 140 trial) で維持されている
- **`requirement_external_*` を baselines.tsv に新規登録** (2 run 合算基準達成、18 行、`established_run_id=v6_baseline_1st+m34`、追加基準 (a) 成立 + (b) 単純平均採用)

### judge 採点を skip した理由

- 本 run は regression mode で「無回帰確認」が主目的。CORE HEALTH (self_exit/test_green/appup_ok/build_complete/crash/iso_break) と CAPABILITY (functional) の PASS 判定のみで regression 判定の必須条件は満たされる
- 単一 run で改善主張はしない (Step 8.5) 原則にも合致
- judge score の補完が必要になった場合は保持 diff (`results/rerun_m34/<trial>.diff`) から Step 5.5 の遡及再採点で後日算出可能 (LLM 再実行不要)
- 集計に要する時間 (35 diff × Claude 精読 + Write) と時間対効果のバランスも考慮

### disk-selfplan の WATCH について

r1/r4 の functional NO は baseline (baseline_scen_repaired_1+2 の run 2 での r1/r4) と同種の失敗モード:
- r1: `df(shellout)` で view から呼ぼうとして 500 (実装が partial)
- r4: helper 定義のみ view から呼ばず (実装漏れ)

これらは disk-selfplan の難しさに由来する既知の変動範囲であり、m34 特有の回帰ではない。次 run 以降の分布安定性を継続観察する。

### 試走で観察された点の追跡

- **pagy の 2nd run 再出現**: 試走 (v6_baseline_1st) で page-selfplan-r2 に初登場した `pagy 8.6.3` は m34 では**再出現せず**、page-selfplan 10/10 全て kaminari。単一 run の LLM 揺らぎだったと 2 run 合算で確認
- **page-selfplan の 3 件 FAIL (試走)**: 試走で functional_rate=0.7 だった page-selfplan は m34 で 10/10 に。実装ゼロ幻覚と pagy 選定は共に単発現象で 2 run 目に再現せず
- **disk-selfplan diff_lines_mean 67.4 (試走) の再現性**: m34 では 37.8 に低下。1st の r5 (Archive.storage_usage + lib/disk_usage.rb で archive_test.rb 300+ 行削除) が単発の外れ値だったと確認

### ハーネス修正の副次効果

タスク 2.5.2 で追加した bench_collect_one.sh の EXEMPT フィルタ (`grep -vE '^.. \.worktree/|^.. \.claude/|^.. report/'`) は m34 collect フェーズで期待通り機能し、false positive の isolation break WARNING が collect ログに一切現れなかった (以前は disk-givenplan-r2〜r5 等で `?? .worktree/` の並びが出ていた)。

### 発見: EXEMPT パターンが 3 箇所で管理される状態になった (今後の運用注意)

タスク 2.5.2 の実施中に、EXEMPT パターンが下記 3 箇所に散在する構造になったことが確認された:

1. `tmp/feat-bench/bench_preflight.py` の `BENCH_POLLUTION_EXEMPT` (Python re.compile リスト、L58-L62)
2. `tmp/feat-bench/bench_build_json.py` の `_ISO_EXEMPT` (Python re.compile リスト、collect_one とは独立に元々存在。fable レビュー由来の isolation break 判定で使用)
3. `tmp/feat-bench/bench_collect_one.sh` の `grep -vE` (今回追加、シェル正規表現直書き)

修正前は 2 箇所 (bench_preflight.py + bench_build_json.py) で二重管理だったが、今回の修正で 3 箇所目 (bench_collect_one.sh) が加わり三重管理になった。今回 bench_preflight.py 側に追加した同期コメントは bench_collect_one.sh との同期のみに言及しており、bench_build_json.py 側との同期は元々どのファイルにも記述がない。**将来 EXEMPT を追加/削除する際は 3 箇所すべてを同時に更新する必要がある**が、同期漏れリスクを軽減するため、次に bench 系ハーネスを触るタイミングで以下のいずれかを検討する余地がある:

- 3 箇所の同期コメントを揃える (最小変更)
- Python 側の `BENCH_POLLUTION_EXEMPT` を共通 module 化し、bench_build_json.py はそれを import、bench_collect_one.sh は Python one-liner を経由してフィルタする (統一)
- あるいは、shell 側で管理するのを止め、bench_collect_one.sh も Python スクリプトに置き換える (Python 側 2 箇所に集約)

いずれも今回のスコープ外だが、副次発見として記録しておく。
