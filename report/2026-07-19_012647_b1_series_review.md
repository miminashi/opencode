# 保護ブランチ直下での無断書き換え問題（B-1）シリーズのレビュー — 見落としとアプローチの再点検

- 日時: 2026-07-19 01:26 JST
- 作成者: Claude (Fable 5)

## 概要

本レポートは、「opencode が保護ブランチ直下で起動された際に、確認なくファイルを書き換えてしまう問題」（B-1）についてこれまでに作成されたレポート群（hallucguard 総括、issue inventory、Phase 0-a 事件再構築、Phase 0-b 再現測定、Phase 1 プロンプト軸探索、Phase 2 本命介入設計）を通読・精査し、見落としているポイントとアプローチ上の懸念を洗い出したレビューである。達成目標は「プロンプトや作業対象プロジェクトの AGENTS.md で『ワークツリーを作成してから作業せよ』と指示されているのに無視される現象の解決」に置いて評価した。

シリーズ全体としては、失敗モードを (a) parent cwd 起動と (b) worktree escape の 2 系統に切り分けた Phase 0-a、(a) 系 100% 再現ベンチの確立、機械分類による介入効果の定量化、fable 独立レビューによる自己修正など、実験としての土台は堅実である。一方で、達成目標に照らすと重大なギャップが 4 つある。第一に、目標の中核である「AGENTS.md 経由の指示」が実験マトリクスに一度も含まれておらず、全実験がタスクプロンプトへの前置で行われている（しかも現行の ytdlor AGENTS.md には worktree 指示自体が存在しない）。第二に、Phase 2 が推奨した aeb1 併記型には実運用への配備経路が無い。第三に、Phase 3 の最優先項目「external_directory=deny 併用」は、(a) 系の direct_write が境界内 write であるため原理的に発火せず、シリーズ自身が 07-13 に確立した知見と矛盾している。第四に、成功指標が途中から「保護総合率」（question を呼ぶだけで edit は実行される asked_first を含む）にすり替わっており、目標に直結する worktree_first で見ると最良値は依然 50% である。

アプローチ面では、「コードガードよりプロンプト介入を先に検証する」という順序自体は、ユーザとの議論による明示的な決定として記録されており問題ではない。ただしその記録には不備がある。順序決定の理由として記録されているのは「柔軟性・可逆性の非対称」のみで、ユーザの実際の動機である「LLM の指示追従性の限界をまず知りたい」は理由としてどこにも記録されていない。また決定記録が Phase 0-a レポートの添付スナップショットにしか無く、Phase 1/2 の本文から経緯を追えない。さらに重要な点として、当時ユーザ合意した移行基準「プロンプトで残差 5% 以下なら prompt のみで完結、許容できなければ permission ガードを設計」に対し、Phase 2 の残差は 40% と大幅超過しており、自ら定めたガード移行条件が既に成立しているにもかかわらず、Phase 2 本文はこの基準との突合を行っていない。

このほか、介入の副作用（正当な直接作業を阻害しないか）が未測定であること、実運用側の再発検知が常設化されていないこと、実事件 3 件中 2 件を占める (b) 系の検証が実運用構造（親リポジトリ内の `.worktree/`）と乖離したベンチ構造でしか行われていないこと、「system prompt レベルは効かない」という一般化が単一変種 n=10 からの早計であることを指摘する。

結論として、Phase 3 は「既定基準の履行」としてツール層の保護ブランチガード実装を本命に据え、並行して AGENTS.md 注入条件をベンチに追加してユーザ目標に直結する未検証セルを埋めることを推奨する。プロンプト介入の知見（例示型が最良、情報提示型は全滅）はガード導入後の UX 設計（ガード発火時の誘導文言）に転用できる。

## 評価できる点

指摘に入る前に、シリーズの強みを記録しておく。

- **失敗モードの切り分け**: Phase 0-a が 3 ファイル事件を「単発」ではなく (a) parent cwd 起動 / (b) worktree escape の独立 2 系統 × 3 件と再構築したことで、以降の介入設計が的を絞れている。通常運用 DB 全期間走査（親直下 write 79 件の発掘）まで遡った調査密度は高い。
- **再現ベンチの確立**: (a) 系 100% 再現（30/30）の評価台は、介入効果を Fisher 検定で判定できる土台として価値が高い。`classify_b1_intervention.py` の 5-way 機械分類と、既存 run 35 trial での分類器妥当性検証も堅実。
- **自己修正の仕組み**: Step 8.5 の 2 run 統計基準、fable 独立レビューによる集計・p 値・解釈の検証（Phase 2 で aeb2 の failure mode 記述と aeb1 の p 値を実際に修正）が機能している。
- **隔離設計**: parent-clone による実 ytdlor の保護は全 Phase 通算 230+ trial で親アクセス 0 件を維持。
- **負の結果の記録**: 情報提示型 4 条件の全滅（50/50 direct_write）や Phase 2b-C の 0/10 を「効かなかった」として明確に記録しており、探索空間の枝刈りとして機能している。

## 見落としているポイント

### 1. AGENTS.md 経由の指示が一度も検証されていない（最重要）

達成目標は「プロンプトや **AGENTS.md** で指示されているのに無視される現象の解決」だが、Phase 0-b〜2a の全介入実験は**タスクプロンプトへの前置（prepend）**で行われており、「AGENTS.md に worktree 指示を書いた条件」は実験マトリクスに存在しない。

この 2 つの経路は opencode 内部で扱いが異なる。AGENTS.md は `packages/opencode/src/session/instruction.ts` の `findUp(file, ctx.directory, ctx.worktree)` で発見され、`Instructions from: <path>` の形で **system prompt に注入**される。一方 Phase 1/2 で 50〜60% の効果を出した介入は全て **user メッセージ（タスクプロンプト）**である。そして Phase 2b-C は「system prompt レベル（`planEnteringSuffix`）への埋め込みは 0/10 で完全無効」を観測した。つまり:

- タスクプロンプト経路（効く: 50〜60%）と system prompt 経路（効かない: 0/10）の分岐が判明している以上、**AGENTS.md 経路の指示は「効かない側」に落ちる可能性が高い**が、注入位置・フレーミング（`Instructions from:` 付きのプロジェクト規約という体裁）は `planEnteringSuffix` と異なるため、独立に測らない限り結論できない。
- 目標に最も直結するセルが未検証のまま、シリーズは task prompt 介入の最適化に進んでいる。

さらに前提事実として、**現行の `/home/ubuntu/projects/ytdlor/AGENTS.md` には worktree 指示自体が存在しない**（ブランチ関連は Rails アップグレード時の `upgrade/rails-X.Y` 命名規約のみ）。「AGENTS.md で指示しているのに無視される」という問題設定に対し、指示を置いた状態の検証も、そもそも指示を置くこと自体も、まだ行われていない。

### 2. 推奨案 aeb1 に実運用への配備経路が無い

Phase 2 の結論は「task prompt レベルで aeb1 併記型（保護総合率 60%）を推奨」だが、実運用でタスクプロンプトに毎回 aeb1 ブロックを前置する主体が存在しない。ユーザが毎回手で書くのは非現実的であり、配備先の候補は (i) AGENTS.md に置く → 指摘 1 の未検証領域、(ii) fork がプロンプトに自動注入する → Phase 2b-C が失敗した領域、のいずれかに入る。つまり**「効いた介入」と「配備できる場所」が現状交わっておらず、推奨が宙に浮いている**。Phase 2 レポートはこのギャップ自体を指摘していない。

### 3. Phase 3 最優先項目のカテゴリエラー: external_directory=deny は (a) 系に効かない

Phase 2 の「Phase 3 への申し送り・優先度高 1」は「permission ガード（`external_directory=deny`）併用の実効性検証: aeb1 の 60% を残 40% の direct_write に対して permission 層で防げるか」とする。しかし (a) 系の direct_write は **cwd（= 保護ブランチ上の作業リポジトリ）内部への write** であり、worktree 境界の**内側**である。`external_directory` permission は境界**外**パスへの tool 呼び出しを制御する機構なので、この write には原理的に発火しない。

これは新しい知見ではなく、[issue inventory (07-13)](./2026-07-13_003357_issue_inventory_isolation_and_scope.md) 自身が「external_directory permission では原理的に防げない（親リポジトリ自体が作業対象＝境界内だから）」と B-1 定式化の根拠として明言した内容である。シリーズ内で確立済みの知見と矛盾する項目が Phase 3 の最優先に置かれており、このまま実施すると「deny を入れたが 40% は変わらなかった」という予見可能な結果に 1 run 分の工数を費やすことになる。`external_directory=deny` の検証が意味を持つのは **(b) 系（worktree escape、絶対パス誘発プロンプト）専用**であり、位置づけの修正が必要である。

### 4. 成功指標のすり替わり: worktree_first で見ると最良値は依然 50%

達成目標「ワークツリーを作成してから作業する」に対応する分類は worktree_created_first のみである。Phase 2 が導入した「保護総合率」は asked_first を含むが、asked_first は fable レビューも指摘した通り「question tool を呼ぶだけで edit tool 自体は全 trial で実行される、ユーザが No と応答する前提の潜在的保護」である。指標別に見ると:

| 条件 | worktree_first | asked_first | 保護総合率 |
|---|---|---|---|
| aexample (Phase 1) | **50% (10/20)** | 0% | 50% |
| aeb1 (Phase 2 推奨) | **5% (1/20)** | 55% | 60% |

つまり**目標達成度（worktree_first）では aeb1 は aexample より大幅に悪く**、「60% > 50%」の改善主張は指標定義に依存する（しかも p ≈ 0.376 で有意でない）。ユーザ不在の自動運用（長時間ベンチ、cron 等）では question に応答する人間がいないため、asked_first の保護は実質機能しない。実際 Phase 2 自身が bench 駆動スクリプトに「permission ダイアログ自動 Reject」を追加した = ハーネスがユーザ役を代行しており、この構図の脆さを自ら示している。目標が「worktree を作ってから作業させる」である限り、主指標は worktree_first に固定すべきである。

### 5. 介入の副作用（false positive 側）が未測定

Phase 0-a は「parent cwd 起動はかつての既定動作パターンで、通常運用 DB に親直下 cwd write が 79 件（正当なメンテ作業）記録されている」「(a) 介入はユーザ運用習慣と衝突し得る」と明確に警告していた。しかし Phase 1/2 の実験マトリクスには**保護介入が正当なケースを阻害しないかを測る対照条件が無い**:

- 非保護ブランチ（feature ブランチ等）の cwd で同じ介入プロンプトを与えた場合に、不要な question / worktree 作成が発生しないか
- ユーザが「main 直下でこのまま直してほしい」と明示した場合に介入がそれを妨げないか

aeb1 は asked_first 55% を「成果」とするが、正当ケースでも毎回 question が出るなら、それは誤検知率 55% の UX 劣化と表裏一体である。介入を実運用に入れる判断には両側の測定が要る。

### 6. 実事件の 2/3 を占める (b) 系の検証が実運用構造と乖離している

3 ファイル事件の内訳は (a) 型 1 件（5/16 AGENTS.md）に対し **(b) worktree escape 型が 2 件**（6/27 Dockerfile、6/29 thumbnail_test）である。Phase 0-b の「(b) 系 0/30 で再現せず → Phase 1 以降 (a) 系のみ対象」という判定は、**親の外（`~/bench-worktrees/`）に置いた worktree + cwd 相対プロンプト**という修復後のベンチ構造での結果であり、次の 2 点が残る:

- 実運用の ytdlor worktree は親リポジトリ**内**の `.worktree/` に置かれている（audit の除外パターン `(?!\.claude|\.worktree)` がその証跡）。親内 worktree では相対パス 1 段で親に届くため、ベンチの 0/30 は実運用構造の安全性を保証しない。
- `external_directory` deny/ask が escape を実際にブロックするかは「AI が境界外を叩かなかったため発火機会なし」のまま。絶対パス指定プロンプトでの誘発検証は Phase 0-b の限界節で予告されてから **2 Phase 連続で先送り**され、Phase 3 申し送りでは（指摘 3 の混同により）(a) 系向けと誤って位置づけられている。

### 7. 再発検知が常設化されていない

3 ファイル事件は発生（5/16〜6/29）から発見（7/9）まで最長約 2 ヶ月潜伏した。現在の検知機構（`bench_preflight.py` の親 dirty ゲート、`audit_parent_access.py`）は**ベンチ run の開始時・締め時にしか走らない**。介入研究と独立に、次のような常設監視は低コストで実装できるが、シリーズのどのレポートにも提案が無い:

- 実運用セッション DB の定期走査（`classify_b1_intervention.py` 相当を cron で回し、保護ブランチ cwd での direct_write を検知）
- ytdlor main の未コミット変更の定期チェック（`git status --porcelain` の通知）

「解決」には介入による予防だけでなく、すり抜けた事例を日単位で発見する仕組みが含まれるべきである。

### 8. 「保護ブランチ」の宣言・検出方法が未設計

実験プロンプトは「main / master / production 等の保護ブランチ」というハードコード表現に依存している。git にはローカルで「保護ブランチ」という概念は無く、実運用でどのブランチを保護対象とするかの宣言方法（config、AGENTS.md、fork 設定のいずれに置くか）は未検討である。[過剰実装レビュー (07-14)](./2026-07-14_204207_bench_excess_patterns_review.md) が推奨した「宣言型スコープガード + 保護ブランチ検知」の設計は、その後 2 Phase を経ても着手されていない。ガード実装（後述の推奨 1）の前提としてこの宣言スキーマの設計が必要になる。

## アプローチ上の懸念

### 9. 順序決定（プロンプト先行）の記録が不完全で、移行基準との突合が行われていない

「コードガードよりプロンプト介入を先に検証する」という順序自体は、[Phase 0-a 添付の NEXT_SESSION.md スナップショット](./attachment/2026-07-14_232447_b1_incident_reconstruction/NEXT_SESSION.md)に「実態計測後のユーザとの議論で明確化」「prompt 教育を先に試したい。機械的制約は強力だが柔軟性に欠ける」と**ユーザ主導の決定として記録されており、判断として問題はない**。issue inventory (07-13) の当初推奨（機械指標整備 → 実態計測 → ガード設計・実装）をユーザ議論で上書きした経緯も追跡できる。ただし記録には 3 つの不備がある:

1. **動機の記録漏れ**: 記録された理由は「柔軟性（/tmp 等への正当な write が拒否される）」と「可逆性の非対称（prompt は 5 分で入替可能、permission は運用合意が要る）」のみである。ユーザの実際の動機であった「**LLM の指示追従性の限界がどのあたりかをまず知りたい**」は、順序決定の理由としてどのレポートにも記録されていない。「能力 vs プロンプト設計の切り分け」という目的付けは Phase 0-b の申し送り（L256-271）で初めて登場するが、これは Claude の分析判断として「プロンプトフェーズ**内部**の設計方針」に位置づけられており、対コードガードの順序理由とは別レイヤになっている。決定の動機が正しく記録されていないと、後続セッション（や本レビューのような第三者）が「ガード後回しは見落としでは」と誤読する。実際、本レビューの初稿がまさにその誤読をした。
2. **記録の所在**: 順序決定と判定基準の一次記録が Phase 0-a レポートの**添付スナップショット**にしかなく、Phase 1/2 の本文には「なぜガードを後段に置いているか」の再掲が無い。本文だけを読むと意思決定の経緯が追えない。
3. **移行基準との突合漏れ（実質的に最重要)**: 同スナップショットには当時合意した判定基準「**C（強介入）で逸脱率が許容水準（残差 5% 以下、要議論）→ prompt のみで運用する方針で完結、permission ガードは保留 / 許容できない残差 → permission ガードを次段として設計**」が明記されている。Phase 2 の最良値でも direct_write 残差は 35〜40% であり、**この基準を大幅に超過 = 自ら定めたガード移行条件が既に成立している**。しかし Phase 2 本文はこの基準に一切言及せず、permission ガードを「Phase 3 の候補の一つ」として別モデル比較・日本語版再挑戦と並列に置いている。基準と実測を突合すれば、Phase 3 の主軸は「候補の選択」ではなく「既定基準の履行としてのガード設計」になるはずである。

### 10. 「system prompt レベルは効かない」の一般化が早計

Phase 2b-C の根拠は「英語 1 変種 × n=10 × `planEnteringSuffix`（plan モード開始時の注入）」のみである。edit が実行されるのは build phase であり、レポート自身が原因候補 (iii) に「plan phase で読まれるが build phase に影響しない」を挙げ、「build phase での reminder 再注入」を優先度中に置いている。つまり観測は「system prompt が効かない」ではなく「**plan 開始時の 1 回注入が build 時の行動に届かない**」とも読める。注入タイミング（build-switch / build agent reminder）、言語（日本語）、フレーミング（AGENTS.md 形式の `Instructions from:`）を変えた検証をせずに「task prompt は効くが system prompt は効かない」という二分法で恒久化案を不採用にするのは早い。この二分法は指摘 1（AGENTS.md 経路の予測）にも波及するため、切り分けの価値が高い。

### 11. 単一モデル・単一量子化への依存

全 230+ trial が Qwen3.6-35B-A3B Q4 単一で実施されている。「例示型 > 行動強制型（2.5 倍）」「情報提示型全滅」「system prompt 無効」といった中核知見は、レポート群自身が繰り返し自認する通りモデル固有の可能性があり、モデル比較は Phase 1 → 2 → 3 と先送りされ続けている。実運用モデルが当面 Qwen 固定なら介入チューニングとしては許容できるが、**fork 恒久機能の採否（Phase 2b-C 不採用、PR 保留）を単一モデルの n=10 で判断している**点は、fork の他ユーザ・他モデルへの影響を考えると根拠が弱い。

### 12. 統計面の留意点

fable レビュー（Phase 2 添付）が多重比較未補正と p 値誤りを既に指摘・修正しているが、それに加えて:

- **baseline 0/10 の床効果**: 対照が 0% のため、どの介入も「改善」方向にしか動けず、効果量の相対比較が過大評価されやすい。
- **run 間変動の大きさ**: aex3 の 60% → 40%（run 1 → run 2）が示す通り、temp 0.6 での n=10 条件間比較はノイズ床が高い。Phase 2a-A で aex2（40%）を「境界域、追認不要」とした判断はこの変動幅の中にあり、レポート自身も「aex2 も追認すれば 50% に収束する可能性」を認めている。
- **推奨の根拠が非有意差**: aeb1 推奨（60% vs 50%、p ≈ 0.376）は Step 8.5 の趣旨（有意な効果のみ効果として扱う）からすると、指標定義の変更（指摘 4）と合わせて二重に弱い。

## 推奨: Phase 3 の再設計案

上記を踏まえた Phase 3 の構成案。番号 0-1 が本命、2 以降が並行・後続。

0. **意思決定記録の整備**: 順序決定の理由（柔軟性・可逆性に加え、ユーザ動機である「LLM の指示追従性の限界の把握」）と残差 5% 移行基準を本文レベルのドキュメント（NEXT_SESSION.md 現行版 + Phase 3 計画書）に再掲し、「残差 40% ≫ 基準 5% → ガード段階へ移行」を正式判定として記録する。
1. **ツール層の保護ブランチガードを fork 本体に実装**: write/edit/patch 実行時に対象パスのリポジトリの現在ブランチを検査し、保護ブランチ（config で宣言、例 `protected_branches: ["main", "master"]`）なら permission を ask に格上げする。これは方針転換ではなく**既に合意済みの移行基準の履行**である。当時の柔軟性懸念（/tmp 等の正当な境界越え write の拒否）は、このガードが「保護ブランチ上の境界内 write」だけを対象とするため `external_directory=deny` より影響範囲が小さい。プロンプト介入と違い LLM の遵守率に依存せず、(a) 系を決定的に塞げる。宣言スキーマ設計（指摘 8）を含む。
2. **AGENTS.md 注入条件のベンチ追加**: aexample / aeb1 相当のブロックを worktree 指示として AGENTS.md に置いた条件（task prompt は a1 のまま）を実験マトリクスに追加する。達成目標に直結する未検証セルであり、指摘 10 の「注入位置・フレーミングの切り分け」も兼ねる。効けば「AGENTS.md に書けば守られる」という運用解が得られ、効かなければガード必須の根拠が完成する。
3. **external_directory=deny 検証の位置づけ修正**: (b) 系専用として、絶対パス誘発プロンプト（例: 実親パスの明示指示）+ 実運用構造（親内 `.worktree/`）で deny の発火・ブロックを確認する。(a) 系の残差対策としては扱わない。
4. **false positive 対照条件の追加**: 非保護ブランチ cwd、およびユーザが直接編集を明示指示するケースで、介入（プロンプト・ガード両方）が正当作業を阻害する率を測る。
5. **再発検知の常設化**: 実運用セッション DB の定期 audit と ytdlor main dirty チェックを cron 化する。介入の効果測定（実運用での direct_write 発生率の推移）にもそのまま使える。
6. **system prompt 経路の再評価**: build phase reminder 再注入 + 日本語版を試してから恒久化案の棄却を確定する。モデル比較（優先度は 1-2 より下）はこの結果と合わせて判断する。

## 結果・所見

- シリーズの実験基盤（2 系統切り分け、100% 再現ベンチ、機械分類、fable レビュー）は堅実で、「情報提示型プロンプトは全滅、例示型のみ 50%」という負の結果群は、それ自体が「プロンプト指示だけでは解決に届かない」ことの実証として価値がある。ユーザが意図した「LLM の指示追従性の限界の把握」という目的は、この意味で既に達成されている。
- 一方、達成目標（AGENTS.md / プロンプト指示の無視の解決）に対しては、(1) AGENTS.md 経路そのものが未検証、(2) 推奨介入に配備経路が無い、(3) 目標対応指標 worktree_first の最良値は 50% で頭打ち、という 3 点から、**プロンプト介入の継続最適化では到達できない**ことがデータ上ほぼ確定している。
- 当時合意済みの移行基準（残差 5%）は既に大幅超過しており、Phase 3 はツール層ガードの設計・実装を「既定基準の履行」として主軸に据えるのが、シリーズ自身の意思決定ルールに最も整合する。
- Phase 3 計画の最優先項目「external_directory=deny 併用」はカテゴリエラーの疑いが濃く、実施前に (b) 系専用への位置づけ修正が必要である。
