# プラン作成ルールの新設とレポート執筆後チェックの追加

- 日時: 2026-07-20 18:13 JST
- 作成者: Claude

## 概要

本レポートでは、`CLAUDE.md` の運用ルールに 2 種類の文書（プラン・レポート）に対する「初稿後の再確認ステップ」を追加した。目的は、初稿段階で入り込みやすい書き漏らしや前後の矛盾を、承認・実行前に自らつぶすルーチンをルール化することにある。背景として、過去に m33 マージレポートの概要集計が後段の表と食い違い、後日 fable レビューで訂正された事例があり（memory `project_fable_review_m33_2026_07_07.md`）、同種の破綻はプラン側でも起きうると考えられた。実際、本セッションの初版プランでは「レポート作成を非対象」と書きつつ CLAUDE.md 冒頭のレポート必須ルールと矛盾しており、プラン段階での自己整合チェックが有効だったことが示された。

実施内容は 2 点で、`## プラン作成ルール` を新設して「プラン初稿後の矛盾チェック」を必須化し、`## レポート作成ルール` 配下に `### 執筆後の確認` サブセクションを追加して「(1) 記載漏れ追記 → (2) 矛盾チェック」の 2 ステップを必須化した。プラン側とレポート側でチェック項目に非対称があるのは、ユーザ要望に忠実に従い、プランでは矛盾チェックのみを言及されたためである。将来、プランにも記載漏れチェックが必要になれば別途追加する運用とした。

検証では変更後の見出し構造を Read + Grep で目視確認し、`## プラン作成ルール` が `## レポート作成ルール` の直前に、`### 執筆後の確認` が `### 添付ファイル` と `### フォーマット例` の間に正しく配置されたことを確認している。次段の課題としては、本ルールが新規プラン・レポートに実際に踏まれているかを継続観察し、必要に応じてチェック観点を追補することを想定する。

## 前提条件・目的

- 目的: プラン・レポートの初稿品質を運用ルールで底上げし、矛盾・記載漏れによる後戻りを削減する。
- 前提: 変更対象は `CLAUDE.md` のみ。既存のセクション本文・memory テンプレート・過去レポートには手を入れない。
- 適用範囲: 本ルール制定後に新規作成するプラン・レポート。過去成果物を遡って再チェックする作業は非対象。

## 作業内容

### 変更 1: 新規セクション `## プラン作成ルール` の追加

`CLAUDE.md` L110（旧位置）の `## レポート作成ルール` 直前に、新規トップレベルセクションを追加した。プランの作成はレポート作成に先行するため、時系列順に並べる意図で直前に配置した。

追加した本文（そのまま挿入）:

```markdown
## プラン作成ルール

plan mode でプランを書いた後、プラン内に矛盾がないか再度確認するステップを設ける。矛盾があれば正しい方に揃えて修正する（どちらが正しいか不明な場合は元の要件・調査結果・参照した既存コード等に立ち返って確定させる）。

チェック観点の例:

- 冒頭の Context / 目的と、後段の設計判断・非対象の切り分けが矛盾していないか
- 「変更対象」と実際の追加内容・検証手順で扱っている対象が食い違っていないか
- 既存ルール（CLAUDE.md 冒頭・memory 記載事項）と矛盾する前提を置いていないか
- プラン内で参照しているファイルパス・行番号・リンクが存在し、記載内容と整合しているか
```

### 変更 2: `## レポート作成ルール` 配下に `### 執筆後の確認` サブセクションを追加

`### 添付ファイル` の末尾行と `### フォーマット例` の見出し行の間に、新規サブセクションを挿入した。執筆完了後のワークフロー手順は本文の書き方ルール（`### レポート本文`）や構造ルール（`### 添付ファイル`）と別性質のため独立サブセクションにし、フォーマット例より前に置くことで「例を見る前に必ず読む」順序を担保した。

追加した本文:

```markdown
### 執筆後の確認

レポートの初稿を書き終えたら、以下の 2 ステップを順に実施する:

1. **記載漏れの確認**: 作業内容・調査結果・実施したコマンド等を振り返り、レポートに書き忘れている事実がないか再確認する。書き漏らしがあれば追記する。
2. **矛盾点の確認**: 追記後の状態で、概要と各セクション、セクション間、本文と表・図等の間に矛盾がないか確認する。矛盾があれば正しい方に揃えて修正する（どちらが正しいか不明な場合は元データ・ログを再確認して確定させる）。

順序が重要: 先に (1) で事実を出揃えてから (2) で整合を取る。矛盾の解消を先にやると、追記で再び矛盾が生じる。
```

### Case Study: 本セッション初版プランで発生した矛盾

本セッションでは初版プランの「非対象」欄に「レポート作成を伴わない — 設定文書 1 セクション追加のみ」と書いていたが、`CLAUDE.md` 冒頭「plan mode で作業の計画を立てる際は、レポートの作成を必ず作業内容に含めること」と直接矛盾していた。ユーザからの「計画に矛盾がないか再度確認してください」を受けて修正し、レポート作成をプランに組み込んだ。この経験はまさに本レポートで制定した「プラン作成ルール」が防ぐべきクラスの誤りであり、Case Study として本ルールが必要である裏付けになった。

## 設計判断

- プラン側は「矛盾チェックのみ」、レポート側は「記載漏れ + 矛盾チェック」と**非対称**とした。ユーザ要望が非対称だったためであり、必要になれば後付けする方針。先回りで対称化しない。
- プラン側の「チェック観点の例」は網羅チェックリストではなく指針。プラン作成コストを過度に膨張させないため。
- レポート側で「順序が重要」を明示。ユーザ要望の骨子（「記載し忘れた事実の確認**後**に矛盾を確認する」）を明文化するため。

## 検証

1. `CLAUDE.md` L110–171 を Read で確認し、以下を目視確認:
   - `## プラン作成ルール`（L110）が `## レポート作成ルール`（L121）の直前にある。
   - `### 執筆後の確認`（L162）が `### 添付ファイル`（L155）と `### フォーマット例`（L171）の間にある。
   - 番号付きリスト・太字マークアップ・コードフェンスが壊れていない。
2. `grep -nE '^##+ ' /home/ubuntu/projects/opencode/CLAUDE.md` を実行し、上記の見出し構造を再確認。
3. 添付プラン `report/attachment/2026-07-20_181304_plan_and_report_post_write_check/plan.md` を配置。

## 結果・所見

- CLAUDE.md への 2 ルール追加は無事完了。既存の見出し順序を壊さず、時系列（プラン→レポート）・読み順（ルール→例）に沿った配置ができた。
- 「プラン作成ルール」新設の妥当性は本セッションの初版プラン矛盾で直接的に裏付けられた。導入初日から具体的な検出事例を持てた点は運用開始上プラスに働く。
- レポート側 2 ステップの順序（記載漏れ → 矛盾）は逆順だと機能しないため、明示的にルール本文に書き込んだ。今後の運用でこの順序が省略されないよう、SKILL 系や feature-bench 系レポートでも意識的に踏むこと。
- 本レポート自身にも新設ルールを適用済み: (1) 記載漏れチェックとして「Case Study」節を追記、(2) 矛盾チェックとして概要記述・作業内容・設計判断間の記述整合を精査した。
