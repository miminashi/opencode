## ⚠ 訂正（2026-08-03 20:45 JST）

**初稿では原因を「電源系の物理障害」と結論したが、これは誤りだった。**
真の原因は**このマシンの拠点と P100 の拠点を結ぶ VPN の障害**である（同日中に復旧）。

P100 は一度も落ちていなかった。復旧後に確認したところ、`uptime` は 1 時間 9 分（19:32 の
起動以降で連続稼働）、親 (8000) と judge (8001) の llama-server は**起動したまま生き残っていた**。
20:10 に発行した `pkill` / `unlock` / `power.sh off` はいずれも届いておらず、
電源は On、lock も自セッションが保持したままだった。

**誤診の原因と、正しい切り分け:**

| 観測 | 初稿の解釈 | 誤り |
|---|---|---|
| 本体も BMC も ARP 応答なし | BMC は待機電源で動くはず → 給電の問題 | **経路が切れても同じ症状**になる |
| `ip route` で `10.0.0.0/8 dev ens19 scope link` | 同一 L2 = 物理的に手元のセグメント | **VPN で L2 が拠点間に延伸**されていた |
| 同一セグメントの 10.1.6.1 が正常応答 | こちら側の設備は健全 → 相手が壊れた | こちら側の端点しか見ておらず反証になっていない |

**決め手は RTT だった。** 復旧後の測定値:

```
10.1.6.1（ローカル）        0.2 ms
10.1.4.8（P100 拠点の BMC）  79〜139 ms   ← 明らかに WAN 越し
```

初稿の時点でこの 2 つを比べていれば「別拠点 = 経路障害もありうる」と分かった。
`scope link` は「物理的に手元」を意味しない。

以下の本文のうち、**「電源系の物理障害」「物理確認が必要」「遠隔復旧不可」とする記述は
すべてこの訂正で置き換わる。** 障害の観測事実（時系列・件数・failure_kind）と、
測定が不成立であるという結論自体は変わらない。

本走は VPN 復旧後の 20:43 にやり直した（結果は別レポート）。

## 概要

Phase 6 の判定雛形はこれまで 139 件の物差しで評価してきたが、その母集団には止めるべき呼び出しがほとんど含まれておらず、「甘くなりすぎ」を検知できないという弱点があった。前セッションで自然発生の逸脱を集めた 290 件の新しい物差しを用意したため、本セッションではこれを使って現行の雛形を測り直すことを目的とした。準備は前セッションで完了しており、走らせるところから始められる状態だった。

本走は予定どおり起動し、GPU の電源投入から judge の準備までは順調に進んだ。しかし開始から約 20 分後、判定サーバへの通信が突然失われた。290 件のうち最初の 55 件までは正常に応答していたが、そこで 4 分間の応答なしが発生し、以降の 234 件はすべて「経路が無い」というネットワーク層のエラーで終わった。プロンプトの長さは失敗した件と成功した件でほぼ同じであり、内容によって失敗したのではなく、ある時刻を境に一斉に落ちたことが確認できた。

問題は判定モデルの能力ではなく、サーバへ届かなくなったことだった。GPU ホストだけでなく、本体の電源とは独立した待機電源で動くはずの遠隔管理装置にも一切応答が無くなっていたため、当初は電源系の物理障害を疑った。**しかしこれは誤診で、実際は拠点間を結ぶ VPN の障害だった**（冒頭の訂正を参照）。判定サーバは終始無事だった。いずれにせよ測定はやり直しが必要で、有効だった 53 件も母集団の先頭に偏っているため部分的な集計にも使えない。

この失敗には、単に運が悪かったでは済まされない危険があった。走行は「正常終了・290 件取得」という記録を残して終わっており、ログを見るかぎり成功したように見えたのである。判定不能だった呼び出しは「許可」として記録される仕組みのため、生の結果を眺めても甘い判定と区別がつかない。そこで、走行が測定として成立したかを事後に検査する仕組みを追加し、本走スクリプトに組み込んだ。今回のデータで実際に不成立を検知できることも確認している。

一方、GPU を必要としない作業は完了した。計画文書の保存先をグローバルに一本化する変更を fork の dev に取り込んだ。作業の過程で、この変更が実はまだコミットすらされていなかったこと、そしてコード中の説明が以前に取り下げた誤った因果のまま残っていたことが判明したため、説明を正しい理由に書き直したうえで取り込んでいる。関連して懸案となっていたベンチの再実行についても、判定コードを読むことで不要と確定できた。

### 得られた知見

1. **`rc=0` と件数一致は走行の成立を意味しない。** 判定不能が捏造 allow として記録される設計
   である以上、完了検知には妥当性の検査を必ず挟む必要がある。今回ゲートを追加した
2. **`No route to host`（EHOSTUNREACH）は「プロセスが死んだ」ではなく「ホストへ届かない」。**
   connection refused と区別することで、llama-server の問題か経路・設備の問題かを切り分けられる
3. **全断したらまず RTT を比べて拠点を判別する。** 本体と BMC が同時に応答を失うのは
   給電障害の署名でもあるが、**拠点間 VPN の断でも同じ症状になる**。今回はこれを取り違えた。
   `ip route` の `scope link` は「物理的に手元」を意味しない（VPN で L2 が延伸されうる）。
   正しい順序は ①RTT で拠点判別 → ②別拠点なら経路を疑う → ③同一拠点で本体だけなら OS ハング
   → ④同一拠点で本体と BMC の両方なら給電
4. **走行時間の短さは成功の指標ではない。** 予想 85〜105 分に対し 35 分で終わったのは効率では
   なく、234 件が 3.1 秒で失敗したためだった
5. **復旧後の再開では `power.sh on` に注意。** 既に On だと iLO が 4xx を返し `exit 1` になり、
   `replay_ctx_arms.sh` は冒頭の `|| die "power on failed"` で即死する。サーバが生きている場合は
   電源投入と llama 起動を飛ばす再開用ラッパー（`tmp/run_ctxb_env_resume.sh`）を使う
