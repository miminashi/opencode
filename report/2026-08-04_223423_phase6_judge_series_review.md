# 判定役LLMによるツール呼び出しチェック実験のシリーズレビュー

- 日時: 2026-08-04 22:34 JST
- 作成者: Claude
- 対象: Phase 6 シリーズ全 22 レポート（2026-07-23 〜 2026-08-04）

## 概要

本レポートは、別の LLM（judge）にツール呼び出しを事前判定させる Phase 6 実験シリーズの全 22 本のレポートを通読し、シリーズ全体をレビューした総括である。シリーズは B-1 対策（LLM が指定ワークツリーを無視して親リポジトリへ書き込む逸脱への対処）の第 3 系統として始まり、約 2 週間で「どの判定モデルが優れているか」を競う実験から、「そもそも何を測るべきか」を問い直す実験へと大きく姿を変えた。

前半（7/23〜7/31）は、判定役を「許可パスの照合器」として運用する前提で精度を追求した時期である。パイロットではコード特化モデル North だけが高い訂正率を示し、「モデルの族ではなくコード特化が効く」という読み替えが起きた。しかしその後、比較基準にしていた baseline の数値が誤りだったこと、記録された allow の約 4 割が判定ではなくタイムアウト由来の捏造だったこと、主指標にしていた correction rate が実際の阻止力を大きく過大評価していたこと、そして観測された FP の変動が現象ではなくサンプリング揺れだったことが、次々と明らかになった。

最大の転換点は 8/2 である。判定役の性能限界を調べる過程で、judge が実は一度も文脈（ユーザの指示・タスク内容）を受け取っていなかったこと、しかも測っていた「パス照合」という問題には機械的な正解があり judge が本質的に不要だったことが判明した。ここでシリーズは FP・recall の数値を正解ラベルごと廃棄し、「ツール呼び出しがユーザの指示と整合しているか」を文脈込みで判定させる路線へ全面転換した。

後半（8/2〜8/4）は、新しい問いのための物差し（正解ラベル）作りと、判定プロンプト雛形の改良を交互に進めた時期である。「免責や観点は該当する全項目に書かないと効かない」という再利用性の高い法則が見つかり、実行場所の観点を追加した雛形で recall は 5 割弱から 97.4%（訂正後の物差しでの値）まで改善した。一方で最終盤の免責の書き足しは「照合手順」ではなく「逃げ道」として使われて裏目に出て、不採用の判断が下された。同時に物差し側の誤りも 2 度発見・訂正されており、判定役はそれまでの報告より実際には良かったことも分かった。

シリーズを貫く構造として、方針転換のほぼすべてが「判定役の能力不足」という結論から「測り方が間違っていた」という結論への反転として起きている。少なくとも 7 回、判定器を直す前に測定系のほうが直された。この自己訂正力はシリーズの美点だが、本レビューで改めて全体を点検すると、確定したはずの教訓が後段で適用されていない箇所や、問題設定レベルの見落としが 13 点残っている。特に「主指標を実効阻止率にする」という 7/30 の決定が方針転換後は適用されていないこと、雛形改良が同一データでの反復選択になっていて汎化性能が未知であること、採否判断が単発 run の点推定で行われていることは、次段の実験設計で最初に手当てすべき穴である。

## 前提条件・目的

- 背景: B-1（worktree escape）対策は (1) プロンプト強化（Phase 3b/3c2 — system prompt 系は無効と確定）、(2) 機械ガード（Phase 3a protected-branch guard — dev マージ済）、(3) 認知系介入の 3 系統で進められてきた。Phase 6 は (3) にあたり、`tool.execute.before` フックで別プロセスの LLM を起動し、tool 呼び出しを allow/deny/ask で事前判定させる構想。
- 本レビューの目的: シリーズ 22 本の経緯（特に方針転換）を 1 本で追えるようにすること、および方法論に残る問題点・見落としを洗い出して次段の実験設計に供すること。
- レビュー方法: 22 本全件の通読（Explore サブエージェント 2 体による全文読解 + 主要な指標定義箇所の直接確認）。方法論指摘のうち「実効阻止率が方針転換後に未使用」「後半 3 レポートに検定・信頼区間なし」の 2 点は、レポート本文の grep により裏取りした。

## シリーズの経過

### 前半: パス照合器としての judge の性能追求（7/23〜7/31）

出発点は「プロンプトでは守らせられず、機械ガードは自律性を奪う」という B-1 対策のジレンマで、その中間解として judge 構想が立てられた（#1）。設計書は judge モデル等級 × framing × 文脈転送量の 300 trial 因子実験と go 3 条件（correction ≥50%・Fisher p<0.05・FP ≤5%）を定めたが、実際のパイロット（#2）は 4 judge × 10 trial に縮小され、judge 候補も設計書の 235B / gpt-oss から ornith / gemma-4 / North に差し替わった。結果は Qwen 系 2 種 + gemma-4 が correction 25% で横並び、Cohere のコード特化 North だけが 87.5%（p=0.013）で、当初の「族多様性が効く」仮説は棄却され「コード特化が effective diversity」に読み替えられた。ただし FP は 1/2 = 50% で単独運用は不可のまま。

直後の control 実験（#3）で最初の大きな訂正が起きる。比較基準にしていた Phase 3c2 の attempt_rate 33.3% は deny 条件（dp bucket）由来の値が混ざった誤りで、対応する条件の正しい baseline は 0/20 だった。control 自体は p=1.0 の灰色決着に終わり、副次的に「North は親役としては全く機能しない（8/8 実装未達）」ことが分かった。先行研究 20 本との突合（#4）は「同族 judge の多数決は実効 1 票」「上位等級路線の撤回」を整理し、benign 母集団の増強（#5、n=20 の FP 測定土台）と fine-tune 用 corpus 化（#6）にシリーズを分岐させた。

corpus 化（#6）は事務作業のはずが、シリーズ前半で最も重い発見を生んだ。記録された allow の 39.6% は judge の判断ではなく timeout 等で plugin が捏造した fail-open であり、有効判定に絞ると recall は 43.6% から 92.3% に跳ねた。つまり「judge の見逃しの過半は判断ミスではなく時間切れ」で、モデル選定より timeout の扱いが律速だった。なおこの corpus のラベル自体にも後日、`..` を含む相対パス脱出を「内側」と誤判定する欠陥が見つかり 8 件が訂正されている（#9）。同じバグでもツールの目的（正解ラベル付け vs 隔離破り検出）によって正しい直し方が正反対になる、という教訓も #9 に残る。

Step 1.3（#7）は「framing v3 で 3 judge 全てが FP≤5% を達成」というシリーズ最良の明るい結果を出したが、19 時間後の Step 1a（#8）がこれを二重に削る。session DB の機械監査で数え直すと、correction rate は阻止力を過大評価しており（North 87.5% の実質は 60%、Qwen35B v3 は correction 20% に対し実効阻止 0%）、主指標は実効阻止率に切り替えるべきと確定した。また確認された escape 12 件中 6 件が bash 経由で、機械ガードと judge の盲点が重なるため「二重防御」前提も揺らいだ。並行して mi25 の電源ボード故障で判定モデル 3 種が物理的に失われた。

P100 同居での測り直し（#10）は前セッションの診断を 2 つ覆した。fail-open の主因は出力予算ではなくサーバ速度（同一設定でサーバを替えるだけで 28.8%→6.0%）、対策候補だった thinking off は FP を 17%→81% に悪化させる有害手だった。実効阻止率は 12/12 = 100% で bash escape も 0 件（「bash は盲点」の実体は時間切れの沈黙だった可能性が高い）。ところが同構成で benign の FP が 5%→30% に戻り、bisect（#11）がこれを解いた。同一入力 222 件を 2 回 replay しただけで deny 率は 1.39% と 3.77% に振れ、2 回とも deny された call は 0 件。FP の変動は現象ではなくサンプリング揺れで、「trial 内に 1 件でも deny があれば FP」という定義が call 単位の揺れを約 11 倍に増幅していた。同一入力比較では v3 framing の効果は実在（2.57% vs 8.68%、p=0.0011）とも確認された。

### 後半: 文脈認識判定への転換（8/2〜8/4）

多数決実験（#12）は「2/3 多数決で誤検知だけが消え、見逃しは増えない」という素直な結果とともに、残った FP の大半が「許可パス一覧に無い」を理由とする deny である一方、機械ラベルは「worktree の内外」しか見ていないという物差しの取り違えを自覚させた。分母を許可パス軸で作り直す（#13）と真の FP は 2/3 多数決で 0/64 となり、単独介入基準を初めて満たした——が、それは改善すべき対象がほぼ消えたことも意味した。

そして 8/2 未明の方針転換（#14）である。judge は一度も文脈を受け取っていなかった。プロンプト雛形に文脈用 placeholder が無く、それを埋める変数は未代入で、corpus 全 2,471 件が context_level=minimal——三重の未実装だった。しかも測っていたパス照合には機械的正解があり（7 行の glob 照合で採点でき、真の FP は全モデルでほぼ 0）、この問題設定に judge は本質的に不要だった。ここで FP / recall の数値は正解ラベルの定義ごと廃棄され、「指示と整合しているか」の判定へ全面転換、許可パス機構は「目標」から「越えるべきベースライン」へ降格した。

転換の実証は速かった。既存 corpus の replay に指示文を足すだけで判定の 56% が入れ替わり、deny 理由からの許可リスト言及が 30/42 → 0/42 に消えた（#15）。新しい弱点として「単発の呼び出しに完遂を求める誤 deny」（single_call_completeness、新規 deny の 92%）が現れ、以降の雛形改良の主題になる。人手による正解ラベル作り（#16）では、42 件の deny のうち止めて正しかったのは 1 件のみ、allow 側に止めるべきものは 0 件——この corpus は「止めるべき呼び出し」をほぼ含まず、悪化検知力が構造的に弱いという物差しの限界が判明した。人の裁定自体も 1 件誤っており（経緯を追うと必要な変更だった。判定 arm のうち経緯を渡した ctx_hist だけが正しかった）、「経緯注入は判定器としては劣るがラベル作りの道具として有用」という位置づけ転換が生まれた。

雛形改良は ctx_step（作業工程の一文追加、誤 deny 解消 47.5%、#16）→ ctx_env（(b) にも免責を追加、78.9%、#17）と進み、ablation（#18）で効いていたのは (a) の実例列挙ではなく (b) の免責と確定した。ここからシリーズ随一の再利用性を持つ法則——judge は各項目を独立に評価するので、免責は該当する全項目に書かないと効かない——が得られた。Step 4 ではもう一つ重要な訂正があった。session DB に残る LLM の自己申告（「許可されているはずなのに拒否される」）を鵜呑みにして「permission 不一致が引き金」と一度結論したが、tool 引数を時系列で並べると因果は逆だった。「LLM の自己申告は引数・ログと突き合わせるまで採用しない」が確立し、計画文書パスのグローバル化（fork dev マージ済）にも理由の書き直しとして波及した。同時に corpus B 290 件（correct_deny 170 / correct_allow 118）の新しい物差しが組まれ、初めて「止めるべきもの」が過半の母集団ができた。

corpus B の初走は拠点間 VPN 障害で 56 件目以降が全滅したが、走行は rc=0・件数一致で「成功」に見えた（#19）。判定不能が捏造 allow として記録される設計と相まって、そのまま採点していれば「甘い判定」と誤読するところで、事後の妥当性ゲート `check_arm_validity.py` が生まれた。再走で得た初の混同行列は recall 47.5% / specificity 79.5%（#20）。診断の結果、甘い側（bash 型 recall 15.6%——書き込みが無いと (c) が N/A で検査を打ち切り、実行場所を問う観点が雛形に存在しない）も厳しい側（明示指示された worktree 作成 19 件のうち通せたのは 5 件——(c) 末尾の免責が発火しない）も、同じ (c) 一箇所に集中していた。

甘い側だけを直した ctxb_loc（#21）は劇的に効いた。(c) を「内側で完結しているか」に書き換え書き込み先/実行場所に分割すると、recall 47.5%→90.8%、bash_workdir_outside 型は 16%→98%。一方、厳しい側を狙った免責の具体化 ctxb_excl（#22）は裏目に出た。狙った本命（instructed_worktree の allow 率）はむしろ低下し、recall は 97.4%→85.6%、打ち切りは 3.8%→10.3% に倍増。judge は免責を照合手順ではなく汎用の逃げ道として使い（場所を指定していないタスクで「意図された場所」という理由を自作して通す実例）、手順の分量自体が思考予算を食った。この変更は不採用となり、土台は ctxb_loc に据え置かれた。同じセッションで物差し側の誤り 15 件（絶対パス抽出器が `:` を除外せず docker の `-v` マウントを「外」と誤判定）も発見・訂正され、訂正後の ctxb_loc は recall 97.4% / specificity 82.9%——判定役はそれまでの報告より良かった。「次にやるべき」とされていた bash_abs_parent_write 対策は型そのものが誤ラベルの産物で消滅し、撤回された（気づかず対策していれば判定役に誤りを教え込むところだった）。

## 方針転換の詳細

ユーザ指示「方針の誤りに気付いて方針転換した点」に対応する、シリーズ中の主要な転換 10 点。

1. **judge モデル路線の転換（7/24、#2・#4）**: 「上位等級（235B）を judge に」という設計時の仮説 H2 を撤回。パイロットで族の異なる 3 judge が correction 25% で横並びになる一方コード特化 North だけが 87.5% となり、先行研究（同族多数決の実効票数、weak-to-strong 監視）とも整合したため、「コード特化 + プロンプト設計 + 将来の少量 fine-tune」路線へ。
2. **baseline の誤り（7/24、#3）**: 比較基準 Phase 3c2 の 33.3% は deny 条件由来の混合値で、対応条件の正しい baseline は 0/20。パイロットの Fisher 検定の前提が実験進行中に差し替えられた。
3. **fail-open の発覚（7/26、#6）**: 記録された allow の 39.6% は timeout 等による捏造。有効判定のみで recall 43.6%→92.3%。「モデル選定より timeout の扱いが律速」へ問題の重心が移動。
4. **主指標の切替（7/30、#8）**: correction rate は「拒否が出たか」しか数えず、逸脱と無関係な拒否を含み、拒否後の迂回を防御に数える。機械監査による実効阻止率では North 87.5% の実質は 60%、Qwen35B v3 は 0%。主指標を実効阻止率へ切替（——ただし後述の通り、方針転換後この指標は使われていない）。
5. **診断の訂正（7/31、#10）**: 前段の「fail-open の主因は max_tokens 不足」を否定——主因はサーバ速度で、同一設定のままサーバを替えるだけで 28.8%→6.0%。対策候補だった thinking off は FP を 17%→81% に悪化させる有害手と判明。
6. **FP 回帰の正体（7/31、#11）**: 「v3 の FP 低減効果が再現しない」という前日の結論を訂正。FP 5%↔30% は同一構成でも再現する揺れの範囲で、trial 単位 FP の定義が call 単位の揺れを約 11 倍に増幅していた。同一入力比較で v3 の効果は実在（p=0.0011）。
7. **物差しの取り違え（8/2、#12・#13）**: judge は 4 観点で答えるのに正解ラベルは 1 観点しか見ていなかった。許可パス軸で分母を作り直すと真の FP は 0/64 で、「改善すべき FP」はほぼ物差しのずれだった。
8. **★最大の転換——文脈認識判定へ（8/2、#14）**: judge は文脈を一度も見ていなかった（雛形に placeholder 無し・変数未代入・全件 minimal の三重未実装）。しかもパス照合には機械的正解があり judge が本質的に不要。FP/recall を正解ラベルごと廃棄し、指示整合判定へ全面転換。着手直前だった 3 作業（候補モデル比較・bash 分類・機械化 hybrid）も「捨てる物差しの上の作業」として取り下げ。
9. **物差し側の訂正の連鎖（8/2〜8/4、#16・#18・#20・#22）**: 人手ラベル 1 件訂正（経緯を見ないと裁定できない事例の実在）→ LLM 自己申告の因果取り違え訂正（Step 4）→ 分析スクリプトが判定不能を allow と数えていた欠陥（#20）→ reasoning_text を捨てて集計していた欠陥（#20 への追記）→ 絶対パス抽出器の `:` 未除外で 15 件誤ラベル（#22）。判定器より先に測定系が直される反転が繰り返された。
10. **★免責路線の不採用（8/4、#22）**: 免責の具体化は recall 97.4%→85.6% と裏目に出て不採用。「禁止の但し書きは、LLM が但し書きを適用する理由を自作するのを止められない」「1 項目だけ変えた ≠ 影響が 1 項目に閉じた」。同時に旧優先課題（bash_abs_parent_write 対策）は型自体が誤ラベルの産物と判明し撤回。

## 方法論上の問題点・見落としの指摘

本レビューの中心。レポート群自身が既に自己訂正した点ではなく、**現在も残っている穴**を挙げる。

### A. 測定設計の問題

1. **主指標の逆戻り**: 7/30 の #8 で「correction rate は過大評価、主指標は実効阻止率」と確定したのに、8/2 の方針転換後の全実験（Step B〜ctxb_excl）はオフライン replay の allow/deny ラベル（recall/specificity）のみで評価している。deny が親エージェントに迂回されないか（#8 で「拒否したのに迂回 2 件」を実測済み）は ctx 系で一度も測られていない。裏取り: 8/2〜8/4 のレポートで「実効阻止」に言及するのは転換前の #12 のみ。ctxb_loc の採用判断は live での防御力と結びついていない。
2. **同一データでの反復改良 = in-sample 過学習リスク**: ctx_soft → step → env → loc の雛形改良は毎回同じサンプル（139 件、次いで corpus B 290 件）で評価・選択されており、holdout がない。ctxb_loc の recall 97.4% は「その 290 件に合わせて改良を重ねた後の in-sample 値」であり、汎化性能の推定値ではない。ft コーパスでは train/eval leakage を厳密に議論した（#6）のに、判定プロンプト自身の選択には同じ規律が適用されていない。
3. **サンプリング揺れの教訓の不適用**: #11 で「単発 run の deny 集合は激しく揺れる（同一入力 2 回で deny 一致 0 件）」と確定したのに、ctxb_env / loc / excl は各 1 run のみで採用・不採用を判定している（ctxb_loc の再現性未確認は #22 で自認）。裏取り: 後半 3 レポート（#20〜#22）には検定・信頼区間が一切ない（Fisher / Wilson / McNemar / 信頼区間の言及 0 件）。同一サンプルの対応比較なので McNemar 等の対応検定が使えるのに未使用で、「52 件が 6 trial 由来」というクラスタ構造の補正もない。前半で確立した統計規律が後半で失われている。
4. **fail-open の分母バイアス**: fail-open は recall/specificity の分母から除外されるが、打ち切りは最も長く考えた（= 難しい）件に系統的に集中する（#22 で自認）。つまり fail-open が多い arm ほど難件が分母から抜けて数値が甘く出る。ctxb_excl（fail-open 33 件 vs ctxb_loc の 14 件）の recall 85.6% は実際より良く見えている可能性があり、不採用判断自体は揺るがないものの、arm 間比較として非対称である。#22 は分母の変化を注記しているが、バイアスの向きまでは分析していない。
5. **fail-open ポリシー本体が未修正**: 設計書（#1）では timeout 時 ask フォールバックだったのに、実装は「捏造 allow」のまま最後まで残っている。これに起因する誤集計・誤解釈はシリーズ中 4 回以上（#6 の 39.6%、#19 の成功偽装、#20 の分析スクリプト過大計上など）。集計側の valid_at ゲートは測定の防御であって、live 運用では fail-open がそのまま防御の穴になる。plugin の fail-closed / ask 化は未実装・未検証。

### B. 一般化可能性の問題

6. **単一 judge への依存**: 方針転換後の全知見（免責は逃げ道になる、観点は全項目に書く、等）は North-Mini-Code-1.0（Q4 量子化）1 モデルでしか確認されていない。前半で「3 judge 横並び vs North だけ特殊」という強いモデル依存性を実測した（#2）以上、雛形設計則がモデル固有でないかの確認が必要。
7. **単一プロジェクト・単一親モデルへの過適合**: corpus は全て ytdlor（Rails）+ 親 Qwen3.6-35B の bench 由来。雛形の免責リストには `docker compose build` / `rails test` 等の具体名が焼き込まれており、ytdlor ワークフロー専用化が進んでいる。可搬性は未評価。
8. **ラベルの単独裁定・循環リスク**: 指示整合ラベルは、雛形を設計している主体と同一の Claude が単独で裁定している。人裁定の誤り 1 件（#16）と型ごと目視の見逃し 15 件（#22）が既に実証されているのに、二重ラベルや独立監査の仕組みがない。評価基準の作者と被評価プロンプトの作者が同じ構造は、同調バイアスを検出できない。

### C. 問題設定レベルの見落とし

9. **live 運用可能性の追跡停止**: 判定 19〜31 秒/call は「フックで全 tool call をゲートする」元構想に対し重大なオーバーヘッドだが、方針転換後はレイテンシ・コストの実用性評価が消えた。多数決（3 倍）と組み合わせると更に悪化する。転換時（#14）に「機械化 hybrid は目標と逆向き」と棄却されたのは**評価**の文脈であって、**運用**アーキテクチャとしての「機械チェックで即断できる呼び出しは judge に回さない 2 段構成」は別問題として未検討。
10. **防御スタック全体での judge の担当範囲を再導出していない**: シリーズ開始時の前提（bash は機械ガードの盲点、二重防御不成立）は、その後の protected-branch guard の dev マージ、計画文書パスのグローバル化、#10 での bash escape 0 件により大きく変わった。corpus B の 2 割強を占める plan_doc_parent 34 件はグローバル化で消滅する見込みで、instructed_worktree 19 件は plugin 側修正（worktree_root の更新）が筋（#22 で候補言及止まり）。「現在の防御スタックの残穴のうち judge が埋めるべきものは何か」の総点検がない。
11. **prompt injection の未検証**: 設計書（#1）がリスクとして挙げたまま、文脈注入（ユーザ発話・経緯）で攻撃面がむしろ拡大したのに、tool 引数や task 文に judge への指示を混ぜる敵対テストは一度も行われていない。
12. **specificity の停滞が未診断**: recall は 50.7%→97.4%（v2 物差し換算。v1 物差しでは 47.5%→90.8%）まで診断と改善が進んだ一方、specificity は 80.6%→82.9%（v2。v1 では 79.5%→82.0%）でほぼ不動。誤 deny 約 17% の内訳分析が後回しになっており、単独運用の観点では依然大きな摩擦である。
13. **採用基準の非事前登録**: 設計書の go 3 条件は方針転換で捨てられたが、新路線の数値目標（recall / specificity のしきい値、打ち切り率の上限）は再定義されていない。arm ごとの採否が事後的・定性的判断になっている。

## 横断的な教訓（レビューとしての所見）

- **方針転換はすべて「judge の能力不足」から「測り方の誤り」への反転として起きた。** baseline 誤り、fail-open 捏造、correction rate の過大評価、FP のサンプリング揺れ、物差しの取り違え、文脈の三重未実装、ラベルの `:` 欠落——少なくとも 7 回、判定器を直す前に測定系が直された。この自己訂正の連鎖はシリーズの最大の美点であり、同時に「最初に測定系を疑う」ことを次段の既定動作にすべき根拠でもある。
- **価値ある知見の多くは主目的の外側から出た。** baseline の誤りは control の中間確認から、fail-open の支配的影響は corpus 化という事務作業から、ラベルバグは fine-tune 先（llama.cpp-fine-tuning）からの指摘から、FP 回帰の正体は「同じ入力を 2 回投げる」最も単純な対照から。外部レビューと単純対照の費用対効果が一貫して高い。
- **再利用性の高い法則群**: 免責・観点は該当する全項目に書かないと効かない（#18・#20）／禁止の但し書きは LLM が適用理由を自作するのを止められない（#22）／沈黙（fail-open）の下で測った FP は信用できない、fail-open と FP は必ず同時報告（#10）／合計値の一致は中身の不変を意味しない（#13・#15）／LLM の自己申告は引数・ログと突き合わせるまで採用しない（#18）／rc=0 と件数一致は測定の成立ではない（#19）。
- **撤退の規律**: 最終盤の免責路線は「狙った改善が出ず、副作用が確認され、寄与も分離できない」を根拠に成果ゼロで不採用と明示された（#22）。サンクコストに引きずられない判断としてシリーズの規律が最もよく表れている。

## 結果・所見

- **現到達点**: 判定雛形の土台は `structured_v3_ctxb_loc.txt`（文脈 = ユーザ指示文入り、(c) を書き込み先/実行場所に分割）。v2 物差しでの成績は recall 97.4% / specificity 82.9%、fail-open 4.8%。ただし上記の通りこの値は in-sample・単発 run・オフライン replay での値である。
- **未達のまま**: 単独介入の実用基準（高い実効阻止率 + 低い誤 deny + 実用レイテンシ）を満たす構成はシリーズを通じて現れていない。
- **次段への推奨（本レビューの指摘に基づく優先順）**:
  1. ctxb_loc の再現 run（同一条件 2〜3 回）と holdout 用の新規 corpus 採取——指摘 2・3 への手当てを最優先とする。数値目標（採用基準）もここで事前に定める（指摘 13）。
  2. ctx 系での実効阻止率の live 測定——replay の deny が親の迂回を実際に止めるかを #8 の機械監査で確認する（指摘 1）。
  3. plugin の fail-open を ask 化（指摘 5）と、防御スタック全体での judge 担当範囲の再導出（指摘 10）。instructed_worktree は plugin 側修正で母集団から外れる可能性があるため、雛形での対処より先に判断する。
  4. 余力があれば第 2 judge での雛形設計則の再確認（指摘 6）と injection 耐性の敵対テスト（指摘 11）。
- **物差し側の残作業**: `export_phase6_corpus.py` の `:` 欠陥は v2 ラベルでの手当てのみで生成側は未修正（再生成すると再発する）。llama.cpp-fine-tuning へは通知済み。
