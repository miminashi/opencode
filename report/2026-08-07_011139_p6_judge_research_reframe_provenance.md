# p6-judge の研究方針を整理 — 判定役は文脈の承認を検査する役へ

- 日時: 2026-08-07 01:11 JST
- 作成者: Claude

## 概要

本レポートは、2026-08-07 のユーザとの議論で明確になった p6-judge 研究の目的と評価枠組みの転回を記録するものである。実験の走行を伴う作業レポートではなく、今後の実験設計の前提となる方針の明文化が目的である。

これまでの実験の中心には、判定役 LLM の 1 回きりの判定を、パス規則から機械的に導いた正解ラベルで採点する枠組みがあった。しかし研究の本来の目的は「モデル同士のかけあわせでどこまでいけるか」を明らかにすることであり、実用的なハーネスを一刻も早く実装することではない。この目的に照らすと、規則で再現できてしまう判定を LLM にやらせて採点しても、LLM が規則に何を上積みしたのかは測れない。8 月 5 日に発覚した物差しの循環は、この構造的なずれをデータの側が先に示していた事例だったと位置づけ直せる。ただし「ずれていた」のは規則由来の正解ラベルに依存した部分であって全実験ではない。直近の段 1 シリーズは正解を手書きの probe とし、規則が原理的に届かない領域が残ることを走行前に確認したうえで測っており、既にこの循環を抜けている。

新しい枠組みでは「ツール呼び出しの時点で、ユーザとの対話は既に終わっているべき」という設計原理を置く。トランスクリプトを承認の台帳とみなし、判定役の役割はパスの正誤判定ではなく、書き込み先の出所が対話履歴で承認されているかの検査に変わる。この構図では deny は失敗ではなく、メイン LLM にユーザへ根拠を取りに行かせる信号であり、評価の対象も 1 回の判定の正誤から「異議 → 提案 → 承認 → 再試行 → 同意」というループが 1 往復で閉じるかどうかに変わる。機械判断で片をつける方針は取らない。ただし機械判断が LLM の判断を強力にサポートできる見込みがある場面では積極的に試す。

既存の実験結果は、この新しい問いの急所を既に特定している。指示の無い書き込みを止める 1 周目の異議はほぼ完璧にできる一方、承認が文脈に現れた後に判定役が同意へ転じる転向率が低いこと、根拠が無いのに文脈にあると読み違えて通してしまう捏造、そして deny を受けたメイン LLM がユーザへの提案ではなく回避に走る行動、の 3 つが計測すべき対象である。さらに走行中の段 1 実験（2 回目）は、新枠組みの言葉では「最初のユーザ発話からの provenance の読み取り」を単体で測る仕事であり、この転回と矛盾しない。足りないのは対象が最初の一発話に限られ、deny の後にユーザの承認が履歴へ加わる過程を見ない点である。

次の実験の入口は、反実仮想ペアに承認ターンを挟んだ 2 ターン版を作り、ループの収束率を測ることである。走行中の段 1 実験は事前登録どおり完走させ、新枠組みへの統合は完走後に行う。なお計測仕様の正本である MEASURE_SPEC.md への本方針の反映は未実施であり、次回の judge 計測の際に更新する。

## 前提条件・経緯

議論の出発点は「『ワークツリーを切って作業してください』という指示を LLM が正しくこなせるか」という問いだった。この指示を字義どおり実行するには、LLM は (1) 既存のワークツリー置き場を探す、(2) 無ければ習慣的な置き場を選ぶ、(3) 選んだ場所でよいかユーザに確認する、という多段の手続きを踏む必要がある。既存の実験結果（条件つき指示の遵守率が規則に負ける・慣習が見えない場面ではもっともらしい捏造が出る・確認手続きは確率的に飛ぶ）に照らすと、この 3 ステップを LLM の裁量として実現するのは悲観的で、当初は「探索と条件分岐を harness 側で機械化し、LLM の判断を狭い選択に縮める」方向を検討した。

これに対してユーザから、前提を変える反案が出た。

> ツールが git worktree コマンドを実行しようとしているとき、ユーザとの対話は既に終わっているという設計になっているべきかもしれません。

目指すフローの例として示されたのが次である。

1. ツール呼び出し（git worktree でワークツリーを作成）
2. 判定役 LLM が異議申し立て（これまでの文脈にそのディレクトリはない）
3. メイン LLM がワークツリーを作成すべきディレクトリをユーザに提案
4. ユーザが承認
5. ツール呼び出し（再試行）
6. 判定役 LLM は、今度は書き込み先のディレクトリが文脈にあるので同意する

あわせて研究の目的も明確化された。**いまやりたいのは「モデル同士のかけあわせでどこまでいけるか」を明らかにする研究であり、現実的なハーネスを一刻も早く実装することではない。** したがって機械判断で片をつける方針は取らない（ただし機械判断が LLM の判断を強力にサポートできる見込みがあるケースでは積極的に試す）。

この明確化を受けてユーザは、これまでの実験について「やりたいことに対して半分くらいずれた実験を繰り返してた気がする」と振り返っている。どこがずれていて、どこはずれていなかったのかの整理は「既存実験結果との突合」節で行う。

## 新しい枠組み

### 設計原理

**ツール呼び出しの時点で、ユーザとの対話は既に終わっているべき。** トランスクリプトを承認の台帳（grant log）とみなし、すべての書き込み先はトランスクリプト内に出所（provenance）を持たなければならない、という不変条件を置く。

### 判定役の役割の変化

| | 従来 | 新枠組み |
|---|---|---|
| 判定基準 | パスが規則・慣習に照らして正しいか | 書き込み先の出所が対話履歴で承認されているか |
| 判定役に必要な知識 | 正しい置き場・慣習 | 対話履歴のみ（正解を知らなくてよい） |
| deny の意味 | 失敗・ブロック | ユーザに根拠を取りに行かせる信号 |
| 評価単位 | 1 回の判定の正誤（recall / specificity） | 「異議 → 提案 → 承認 → 再試行 → 同意」の 1 往復が閉じるか（ループ収束率） |

この置き換えにより、従来の枠組みで問題だった「慣習の捏造」（LLM が知らない慣習をもっともらしく推測する）は、正解を知らなくても捕まえられるようになる。根拠のない選択は正誤を判定されるのではなく、ユーザへ差し戻される。初回の deny はむしろ設計上望ましい動きになるため、FP / FN の意味づけ自体が変わる。

### 研究の核心

**「言及」と「承認」の区別。** ディレクトリ名が会話に登場したことと、そこへの書き込みが承認されたことは別である（調査の途中で言及されただけのパス、別目的で出てきたパス）。文字列一致の機械判定はまさにここで破綻するため、この区別こそモデル同士のかけあわせで測る価値のある能力であり、機械判断を封印する方針とも整合する。

また、承認がどんな言い回しで文脈に残るか — メイン LLM の提案文の書き方 — が判定役の転向率を左右すると見込まれる（後述の fact naming の知見の延長）。これも「モデル同士の相互作用」の一部として観測対象になる。

## 既存実験結果との突合

### ループの急所は既に測れている

新枠組みの成立条件は 1 周目の deny 性能ではなく 2 周目以降にある。既存データが特定している急所は 3 つ。

1. **承認出現後の転向率（最重要）。** 反実仮想ペア検定（[2026-08-05 レポート](./2026-08-05_011203_phase6_location_facts.md)）で、指示文から作業場所の記述だけを外した 19 組を両側測定した結果、`ctxb_loc` は指示なし側 deny 19/19 と完璧だった一方、**指示あり側の allow は 5/17**（約 7 割を deny）だった。つまり「外側なら一律 deny」に近い方針であり、文脈に根拠があっても同意へ転じない。このままでは提案フローの 5〜6 手目（承認後の再試行 → 同意）が成立せず、**ループが収束しない**。1 周目の異議はできる、勝負は 2 周目の転向、というのが現在地である。

2. **根拠の捏造。** fail-open 分析（[2026-07-26 判定ログのコーパス化](./2026-07-26_181945_phase6_verdict_corpus_export.md)）で **allow の 39.6% がもっともらしい捏造**だったことが分かっている。「このディレクトリは文脈で承認されている」と判定役が幻覚すれば、承認なしで通ってしまう。急所 1 と 2 は同じ物差し（ペアの両側報告）で対にして測る。

3. **deny 後のメイン LLM の行動。** [Phase 3c2（2026-07-20）](./2026-07-20_211311_b1_phase3c2_prompt_v2.md)で **deny の bash bypass が 45%** 観測されている。異議を受けたメイン LLM の選択肢は「ユーザに提案する」「回避を試みる」「承認済みだと自己申告して再試行する」の 3 つあり、望ましいのは最初の 1 つだけである。これは判定側でなく実行側の行動として新規に計測する必要がある。

### 過去実験のどこがずれていて、どこはずれていなかったか

**ずれていたのは、規則由来の正解ラベルに依存した one-shot 判定の枠組み（corpus B 系）である。** corpus B の正解ラベルはパス規則の関数として作られており、LLM を使わない約 20 行の規則が判定役 LLM を recall・specificity の両方で上回った（規則 recall 100% / specificity 98.5% に対し `ctxb_loc` 97.4% / 82.9%。[2026-08-05 レポート](./2026-08-05_011203_phase6_location_facts.md)）。規則で足りる判定を測っても LLM の上積みは測れない — この循環の発覚は、「規則で解ける問題は本来の問いではなかった」ことをデータの側が先に示していた事例と位置づけ直せる。

**一方、段 1 シリーズはこの枠組みに該当しない。** 段 1（最初のユーザ発話から作業場所を抽出する LLM）の正解は手書きの probe であり、走行前に規則ベースラインを測って規則が原理的に届かない領域（H 軸: 参照専用と明記された場所を書き込み先にしない）が残ることを確認したうえで走らせている。新枠組みの言葉では、段 1 は「最初のユーザ発話からの provenance の読み取り」を単体で測っており、H 軸が測っているものは「言及 vs 承認」の区別と同じ性質である。足りないのは**対象が最初の一発話に限られる**点で、2 ターンループでは deny の後にメイン LLM の提案とユーザの承認が履歴へ加わるが、段 1 の入力設計はそれを見ない。この整理は走行中の実験の[中間報告](./2026-08-06_222200_phase6_stage1_v2_branch_fact.md)（§走行中に届いた研究目的の再定義）に暫定的な形で記載済みであり、本レポートはそれを確定させるものである。

要するに、ずれていたのは「問い」であって計測技術ではない。反実仮想ペアのコーパス・両側報告・盲検監査・事前登録といった手法と、急所の位置（転向率・捏造・回避）は、すべて新しい問いへの資産としてそのまま流用できる。

### 承認の言い回しが転向率を左右する見込み

fact naming の知見（2026-08-05: 機械解決した場所の呼び名に `main` / `repository` を含めただけで recall 97.5% → 45.8%、呼び名を中立な語に差し替えるだけで 38 件が反転して 81.1% に回復）から、判定役は入力の**語感**に強く引きずられることが分かっている。2 ターンループでは「承認」はメイン LLM の提案文とユーザの応答という自然文で履歴に残るため、その言い回しが判定役の転向率を左右するはずである。これは統制すべきノイズであると同時に、メイン LLM の提案文生成能力という観測対象でもある。

### インフラ面の前提

判定役が「呼び出しごとの対象」と「ユーザ指示」を見られることが新枠組みの前提だが、この配線は 2026-08-05 の改修（呼び出しごとの書き込み先・実行場所の機械解決と注入、`{{user_task_summary}}` の配線）で済んでおり、インフラ面の障害はない。

## 今後の作業

1. **2 ターン動的ループの物差しを作る。** 反実仮想ペア 19 組をプロトタイプとし、deny の後に「メイン LLM の提案 + ユーザの承認」ターンを挟んだ版を作る。主指標は**ループ収束率**（deny → 提案 → 承認 → allow が 1 往復で閉じた割合）、副指標に急所 1〜3 をペアの両側報告で測る。
2. **走行中の段 1 実験（2 回目）は事前登録どおり完走させる。** 事前登録した問い（1 回目の失点は能力の天井か入力設計の天井か）は 1 回目の未解決点に直接答えるもので、中断して設計し直す理由がない。新枠組みへの統合（段 1 を 2 ターン入力へ拡張するか等）は完走後に行う。
3. **`tmp/p6-judge/MEASURE_SPEC.md` への反映。** 計測仕様の正本への本方針の反映は未実施である。次回の judge 計測の際に、ループ収束率を含む形へ更新する。
