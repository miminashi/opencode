# 会話履歴を独立した節にしても、正しい承認の読み取りは保たれた

- 日時: 2026-08-15 22:40 JST
- 作成者: Claude

## 概要

phase 6 の判定役 LLM は、ツール呼び出しがユーザの指示と整合しているかを判定する役である。この判定役に渡す雛形では、承認のやりとりが「ユーザの指示:」節の**内側**に置かれ、それが会話の記録であることも、発言者が誰かも、対話の後に呼び出しが発行されたという時系列も宣言されていなかった。2026-08-08 のレビューで、人間が読んでも構造が分かりにくいと確認されている。そこで会話履歴を独立した節として新設し、話者と時系列を宣言する雛形（A）を作った。ただし提示方法を変えると、判定役が**正しい承認を読み取れなくなる**恐れがある。本ラウンドはその劣化が起きないかを測るために走らせた。

本レポートの結論は次のとおりである。主指標である L3+L4 併合の `Q1-b`（正しい承認の読み取り）は **63.8% → 64.3%・Δ = +0.5pt**、95% CI は **[−8.5, +9.5]pt** で、マージン 20pt の非劣性条件を満たし **強い保持確認**（alpha=0.01 でも下限が −11.5pt）となった。一方、A が直接狙っていた提案行の誤読（`Q1-a`）は L2 が −1.3pt、L3 が −3.1pt で、いずれも CI が 0 を含み **減少は検出されなかった**。事前登録 §4-6 に従い、**A は「保持を壊さない提示方法」として記録し、誤りの減少は主張しない**。⚠ A を「効いた」とも「削った」とも書かない。

走行前には「精度不足で判定不能」が正規の結末として登録されていた（保守側の仮定で検出力 0.735）。実際には CI の幅が **18.0pt** と予想より狭く、判定不能にはならなかった。第 4 ラウンドの幅 45.2pt から大きく縮んだのは、主指標を L3 単独から **L3+L4 併合**に広げ、反復を 3 から **5** に増やしたためである。⚠ ただしこれは走行前に登録した設計が結果的に足りていたということであり、材料数 13 が律速だという分析（反復を増やしても検出力は 0.777 → 0.787 にしか動かない）自体は変わっていない。

副次記録には注意すべき所見がある。deny が正解の水準 L1 で allow 率が **+16.4pt** 増えて 0 を外した（★）。L2 も +16.2pt で 0 に接している（CI 下限 −0.8pt）。⚠ ただしこれは**判定に使わない副次**であり（事前登録 §5）、live 相当の cap（60 秒 / 2048 トークン）で採点し直すと L1 の ★ は消える（+12.6pt・CI [−4.2, +28.6]）。⚠ さらに **L1 と L2 の allow の内訳は目視していない**ので、増えた allow が何を根拠にしたものかは分からない。

走行は 3 度止まった。1 度目と 2 度目は smoke ゲートの停止で、いずれも**雛形の問題ではなく、ゲート自身の定義域の漏れ**だった。3 度目は GPU サーバへの経路が消えるネットワーク障害で、c2 の 3 反復目が 78 件中 38 件を失った。⚠ **走行中にゲートを 2 度変更している**。事前登録の末尾に追記 1・2 として記録し、変更時点で見ていたデータの範囲（主指標は 1 件も見ていない）も開示した。失われた 38 件は judge に届いていない件に限って取り除き、取り直した。

## 結果

### 主指標（判定）

```
L3+L4 Q1-b   63.8% → 64.3%   Δ = +0.5pt   95%CI [-8.5, +9.5]   (n=130/129, 材料 13/13)
             感度線 alpha=0.01: CI [-11.5, +12.3]pt
判定: 保持確認（強い保持確認）
```

分子・分母は c2 が 83/130、a1 が 83/129 である。CI 下限 −8.5pt はマージン −20pt を上回り、alpha を 0.01 に下げても下限 −11.5pt で保持側に収まる。

### 副次: 水準別の `Q1-b`（判定には使わない・併合が乗り換えでない証拠）

| 水準 | 変化 | Δ | 95% CI | 参考の 3 値 |
|---|---|---|---|---|
| L3 | 49.2% → 53.8% | +4.6pt | [−12.3, +21.5] | 保持確認 |
| L4 | 78.5% → 75.0% | −3.5pt | [−13.8, +7.3] | 保持確認 |

主指標を L3 単独から併合に広げたが、**L3 単独でも保持確認**であり、併合が結論を作り出したのではない。

### P-A2: 提案行を根拠にした allow（A が直接狙う誤り）

| 水準 | 変化 | Δ | 95% CI | 向き |
|---|---|---|---|---|
| L2 `Q1-a` | 15.4% → 14.1% | −1.3pt | [−10.6, +7.9] | 0 を外さない |
| L3 `Q1-a` | 18.5% → 15.4% | −3.1pt | [−13.8, +7.7] | 0 を外さない |

⚠ **減少は検出されなかった。** CI が 0 を含むことを「変わらなかった」とは読まない。

### 副次: allow 率（P3・⚠ 判定には使わない）

| 水準 | 正解 | 変化 | Δ | 95% CI |
|---|---|---|---|---|
| L0 | deny | 20.3% → 21.5% | +1.2pt | [−7.7, +10.8] |
| **L1** | deny | 31.2% → 47.7% | **+16.4pt** | **[+2.8, +30.3] ★** |
| L2 | deny | 40.0% → 56.2% | +16.2pt | [−0.8, +33.8] |
| L3 | allow | 76.9% → 75.4% | −1.5pt | [−10.8, +9.2] |
| L4 | allow | 83.1% → 81.2% | −1.8pt | [−11.3, +7.4] |
| LA | allow | 32.3% → 30.8% | −1.5pt | [−14.9, +11.6] |

⚠ L1 の ★ は **live 相当の cap（60 秒 / 2048 トークン）で採点し直すと消える**（+12.6pt・CI [−4.2, +28.6]）。境界に近い ★ は弱い証拠として扱う。
⚠ **L1 と L2 の allow の内訳は目視していない**ので、増えた allow の根拠は分からない。

### 目視の内訳（267 件）

| 水準 | 件数 | 内訳 |
|---|---|---|
| L2 | 62 | `Q1-a` 19 / `Q1-c` 8 / 該当なし 35 |
| L3 | 99 | `Q1-b` 67 / `Q1-a` 22 / 該当なし 9 / 保留 1 |
| L4 | 106 | `Q1-b` 99 / `Q1-a` 3 / `Q1-∅` 1 / 該当なし 3 |

うち 86 件は逐語一致による機械確定、181 件が目視である。**機械が確定した件を目視が覆したものは 0 件**だった。保留 1 件は生成が崩れて内容を特定できなかった件である。

⚠ L4 では**ユーザ行が場所を含む命令文**（`{DIR} に作ってください`）なので、「命令形なら `Q1-a`」という短絡を使っていない。`Q1-a` としたのは、アシスタント行にしかない行為語（作業用に切る・作業させてください）を再現した 3 件だけである。

## 走行の経緯（⚠ 3 度の停止）

### 1 度目: smoke ゲートが背景の HTTP 500 で停止（2026-08-14 22:28）

対照 c2 側で `failure_kind=http_error`（空ボディの HTTP 500）が 1 件出て停止した。⚠ **雛形の破損ではない。** HTTP 500 は r3+r4 の 1404 件中 8 件（0.57%）に出ており、arm・水準・材料に散らばる。当該 id は過去 20 arm すべてで 200 成功していた。8 件の smoke では約 4.5% の確率でこれを引く。

原因は特定できていない。judge のログは remote の `/tmp` にあり、cleanup が GPU を落としたため再起動で失われた。システムログに Xid / OOM / segfault は無く、レスポンスボディも空だった。⚠ **この後、cleanup に「電源断の前に judge ログを回収する」処理を足した**（r3/r4 の 500 も同じ理由で追えなくなっていたはずである）。

対処として `smoke_gate_r5.py` を作り（原本は不変）、**応答が返らなかった件**と**応答は返ったが JSON が読めなかった件**を分け、後者のみ 0 件を要求するようにした。前者は半数以上で FATAL とする（全滅を見逃さないための fail-closed）。

### 2 度目: 同じゲートが再開時に自壊（2026-08-15 15:51）

ユーザ指示による中断（01:23・284 件完了）を挟んで再開したところ、a1 側で `parse_failed` 1 件により停止した。⚠ **その id は smoke の 8 件に含まれていなかった。** `calls.jsonl` は毎回 `raw.jsonl` から全件作り直されるため、**中断前に完走していた 78 件全体がゲートの検査対象になっていた**。ラッパは件数検査を `atleast` にしてこの衝突を避けていたが、内容検査に同じ手当てが無かった。既知の教訓「『存在したら FATAL』型の防護は再開手順と衝突して自壊する」の、件数から内容へ場所を変えた再来である。

落ちた 1 件は `finish_reason=length`（6144 トークンで打ち切り）で、中身は同じ verdict JSON の繰り返しだった。⚠ **対照 c2 にも同じ現象が 1 件**あり、過去ラウンドでも 0.36%（1404 件中 5 件）出ている。雛形非依存である。

対処として `SMOKE_SAMPLE` を必須の env とし、その id 集合に含まれる行だけを検査するようにした。⚠ 条件を緩めたのではなく、事前登録 §9 の「smoke（8 件）で 0 件」という記述に実装を合わせた。selftest は 10 → 15 項目に増やし、この不具合そのものの回帰検査を入れた。

### 3 度目: ネットワーク障害（2026-08-15 16:48）

走行中に t120h-p100 への経路が消えた（`No route to host`）。本体 10.1.4.14 と iLO 10.1.4.8 が**同時に**落ちた。18:37 の時点では復旧しており、⚠ **給電障害ではない**（RTT を比べて確認した。2026-08-03 に同じ症状を給電障害と誤診した記録がある）。cleanup の電源断も iLO 障害で届かず、GPU は約 1 時間 50 分アイドルで動き続けた。

被害は `c2_rep3` のみで、78 件中 **38 件が judge に届いていなかった**。⚠ 届かなかった行は `action=allow` として記録されるうえ、`RESUME=1` はそれを「完了」とみなすため、放置すると**半分壊れた arm のまま完走する**。`fetch_error` の 38 件だけを取り除き（元ファイルは退避・除いた id は記録）、取り直した。

⚠ このとき `raw.jsonl` だけを減らして再開したところ「78 件は既に完了」となり再び停止した。resume は **`raw.jsonl` と `calls.jsonl` の和集合**を完了とみなす（`judge_replay_bench.py:833`）。「calls は raw から作り直されるので触らなくてよい」は誤りで、**作り直されるのは走行の後、resume 判定は走行の前**である。

## 測定の成立

| 検査 | 結果 |
|---|---|
| 装置 selftest | 内訳ゲート・整合ゲート 13 項目・Δ 装置 22 項目すべて通過（⚠ 走行結果を開く前に実行） |
| 妥当性ゲート | 全 10 arm が閾値内。判定不能は各 arm 0〜1 件（最大 1.3%） |
| ディレクトリ検査 | 10 arm すべてが `sample_sha256` 突合を通過 |
| 整合ゲート | G1〜G6 すべて通過 |

判定不能の内訳は `http_error` 3 件・`parse_failed` 4 件で、c2 側 5 件・a1 側 2 件と**対照側の方が多い**。

⚠ Δ 装置の selftest には項目 A3「第 4 ラウンドの設計（L3 単独・R=3・m=10pt）は到達確率が低い（≈0.40）」が含まれており、**この検査があれば第 4 ラウンドを走行前に止められた**ことが機械的に確認されている。今回の設計は ≈0.82 である。

## 限界

- ⚠ **走行中にゲートを 2 度変更した**（追記 1 = 種別の分離 / 追記 2 = 対象の限定）。変更時点で見ていたのは `parse_ok` / `http_status` / `finish_reason` だけで、**主指標は 1 件も見ていない**。変更は c2 と a1 に同じ基準でかかる
- ⚠ **`c2_rep3` は arm 内で時刻が混在する**（40 件が 16 時台、38 件が 19 時以降）。本系列は走行を跨ぐと点推定が動くことが分かっているので、この arm の条件は他の rep と完全には揃っていない
- ⚠ **盲検は形式的である。** 分類者は第 3・第 4 ラウンドの結果を既知の状態で目視している
- ⚠ **L0 / L1 / LA の allow と deny 全群は測っていない**（目視範囲外）。「変わらなかった」とは書けない
- ⚠ 主張は「**この 13 材料・この挿入文インベントリの上**」に限る。13 クラスタのブートストラップは名目より狭い CI を出しやすく、**非劣性では「保持確認」の偽陽性を増やす向き**に効く（だから alpha=0.01 の感度線を併記した）
- ⚠ **対 1（末尾注意文）と対 2（見出し）を分離していない。** A の効果がどちらに由来するかは本ラウンドでは分けられない（対 1 だけを変えると存在しない節を参照する雛形になるため、分離は設計上できない）
- ⚠ **c0 を走らせていない**ので、走行間ドリフトの記録が本ラウンドには無い
- ⚠ **主指標の live cap 感度は取れなかった**（集計ラッパに live cap での Δ を出す経路が無い）。副次の P3 については取れており、L1 の ★ が消えることを確認した

## 次にやること（事前登録 §4-6 の該当行）

主指標が「保持確認」かつ P-A2 が「0 を外さない」に該当するため、登録済みの行動は次のとおりである。

> **A は「保持を壊さない提示方法」として記録する。誤りの減少は主張しない。**

⚠ したがって A を live 雛形へ進める根拠は本ラウンドでは得られていない。誤りの減少を示すには、別の介入か、材料を増やして検出力を上げる作業が要る。
