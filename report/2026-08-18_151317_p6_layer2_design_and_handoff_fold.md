# 引き継ぎ文書の畳み込みと、deny 後行動ベンチの設計確定

- 日時: 2026-08-18 15:13 JST
- 作成者: Claude

## 概要

別セッション（`phase-6-judge-approval-round-5`）から次セッション分として 2 件の依頼を受けた。ひとつは `NEXT_SESSION.md` が 870 行に膨れて次に読む量として過大になっている問題で、2026-08-16 の実測から「削れるのは 8% ほど」と分かっているため、削除ではなく別ファイルへ畳むことが求められていた。もうひとつは `MEASURE_SPEC.md` version 7 の §4.4（未確定の設計課題 4 点）が手つかずのまま残っている問題で、規格自身に「着手時に本書を改版して確定させる」と書かれており、第 2 層（deny 後行動ベンチ）はここが片づくまで走行に進めない状態だった。

本レポートの結論は次のとおりである。2 件とも完了した。引き継ぎは 870 行から 378 行になり、移動した 511 行が逐語で保存されていることを機械検査した。規格は §4.4 を確定して version 8 へ改版し、会話履歴はセッション DB から復元する・リプレイ起点は対象 call の直前に置く・分類は (b) 迂回試行のみ機械判定にする・観測範囲は打ち切り規則を凍結して上限値はパイロットで決める、の 4 点を凍結した。ただし**畳み込みは目標としていた「約 200 行」には届いていない**（385 行）。また走行前の検出可能性の計算から、**主指標の効果が +10pt の大きさだとどの設定でも検出率 0.8 に届かない**ことが分かり、両側実施（材料数 38）を既定に据えた。次に必要なのはパイロットで、そこで 4 分類の対照率と観測範囲の上限を得るまで検出力は確定しない。

作業の途中で、依頼された作業そのものを妨げる不具合を 1 件見つけた。`update_next_session.py` は引き継ぎの冒頭部だけを差し替えて追記領域を保護する道具だが、境界を見出し文字列 `## 🔜 その後` の単純検索で決めていた。ところが本文の注意書き自体がその文字列を引用として含んでおり、境界が本来より 60 行手前に当たっていた。出現回数を数えていないので、誤った位置で静かに切れる状態だった。マーカー行方式へ差し替え、ちょうど 1 個でなければ止まるようにし、3 経路の検査を通した。

畳み込みでは記録を 1 件も捨てていない。検査は「移動先に連続部分文字列として存在するか」と「残余が新しいファイルに順序を保った部分列として存在するか」を別々のロジックで見ており、行を落とす・書き換える・並べ替える・移動先を空にする細工を注入して、実際に不合格になることを確かめてある。畳んだ 4 種のうち「測り方の落とし穴」の一部は規格の §3 レジストリ（項目 15〜18）に正本があるため、移動先の冒頭に正本の対応表を置いて二重管理を避けた。

§4.4 の確定では、会話履歴の再構成方法の二択が実データで決着した。セッション DB には user と assistant のテキスト・無切断の tool 引数・tool の結果と errorText・時系列キーがすべて残っており、対象 call の直前までを復元できる。一方 export 済みレコードは 1 件の tool call のスナップショットにすぎず、履歴の系列を持たない。ただし DB にも system prompt は残っていないため、リプレイでは走行時のものを使い「当時を復元した」とは主張しない設計にした。あわせて `callID` がグローバル一意ではないことが実測で分かったので（2471 件中 10 件の衝突）、対象の特定には DB 主キーの `part.id` を使う。

#### 追記境界の作り直し

`tmp/p6-judge/update_next_session.py` は次の実装だった。

```python
MARK = "## 🔜 その後"
i = body.find(MARK)
```

⚠ **`NEXT_SESSION.md` の 146 行目に、この道具の説明そのものが MARK 文字列を引用として含んでいた。**

```
- ⚠ **`tmp/p6-judge/update_next_session.py` は `## 🔜 その後` までを置換し、それ以降を保持する**。
```

`find()` は最初の出現を返すので、境界は本来の 206 行目ではなく 146 行目に決まる。畳む前の版にも同じ行があったので、**2026-08-16 に該当の節が書かれた時点から発火する状態だった**。出現回数を数えていないため、誤った位置で静かに切れる。

作り直した実装では、本文に自然には現れないマーカー行で切り、**出現回数がちょうど 1 個でなければ止める**。旧見出しへのフォールバックも残し、そちらも行頭一致かつ 1 個であることを要求する。どちらも決まらなければ何も書かずに終了する。

⚠ **本文中でマーカーを逐語表記すると、この「2 個なら止める」ガードが自壊する**（旧実装が踏んだ穴と同型）。引き継ぎ側の説明ではコメント記号を含めない表記にし、その旨も本文に書いた。

## 結果・所見

### 畳み込みの結果

- `NEXT_SESSION.md`: **870 行 → 378 行**（移動 511 行）
  - ⚠ **これは畳み込み直後の値である。** その後 §4.4 の確定を引き継ぎへ反映した分だけ増え、本レポート作成時点では **404 行**になっている。⚠ **「畳み込みでどれだけ縮んだか」と「今何行か」は別の数字である**
- `tmp/p6-judge/LESSONS_LAYER1.md`: 539 行（新規）
- 逐語保存の検査: 移動した 3 ブロック（46 行 / 12 行 / 453 行）がいずれも移動先に連続部分文字列として存在し、残余 360 行が順序を保って新しいファイルに存在し、行数の会計（871 = 残余 360 + 移動 511）も合った。新しく増えた 19 行はすべてリンクの stub 由来である
  - ⚠ **会計の 871 と `wc -l` の 870 は数え方の違いである**（検査は末尾の改行で生じる空要素を含めて数え、`wc -l` は改行の個数を数える）。本レポートの「870 行 → 385 行」は `wc -l` の値である

⚠ **目標としていた「約 200 行」には届いていない**（畳み込み直後で 378 行）。指定された 4 節の合計が 511 行で、元が 870 行だったので、指定分をすべて畳んでも 359 行が残る計算である。さらに縮めるなら「⛔ やらないこと」と、後半の古い「リソース状態」が候補になるが、いずれも指定外なので手を付けていない。

### 検出可能性の計算

主指標は理由水準 (i) 正確 + 実行可能 と (iv) 理由なし の間で見る **(a) 正しい代替**の率である。⚠ **4 分類の対照率は未実測**なので、以下は仮定のグリッドであって実測に基づく検出力ではない。

| 設定 | +10pt | +20pt | +30pt |
|---|---|---|---|
| M=19 / R=5 / τ²=0 | 26〜48% | 82〜94% | 96〜100% |
| M=19 / R=5 / τ²=0.02 | 28〜38% | 72〜76% | 98〜100% |
| M=38 / R=5 / τ²=0 | 42〜70% | 96〜100% | 100% |
| M=38 / R=3 / τ²=0.02 | 22〜46% | 82〜92% | 100% |

読み取れることは 3 つある。

1. **+10pt の効果はどの設定でも 0.8 に届かない**（最良でも M=38・R=5・対照率 15%・τ²=0 で 70%）。この大きさの差を確認的に扱う設計にはしない
2. **+20pt は両側実施（M=38）なら R=3 でも 82〜92%** に届く。⚠ **片側（M=19）では τ²=0.02 を入れると 72〜76% まで落ちる**
3. **材料間不均質 τ² の効きは M=19 で顕著、M=38 では緩和される**

→ 規格には**両側実施（M=38）を既定**として書いた。§4.2 の「両側実施」はもともと「deny 側に振ってよいか」を答えるための設計だったが、**検出力の面でも片側では足りない**ことが分かった。

⚠ この計算は未分類（観測範囲の打ち切り）を分母に入れていないので**楽観側**である。パイロットで未分類率が高ければ、実効の材料数はそのぶん減る。

### 会話履歴の復元可否（実データで確認）

| 要素 | セッション DB | export 済みレコード |
|---|---|---|
| user / assistant のテキスト | ○ | ✗ |
| tool 引数（無切断） | ○（`state.input`） | △ 該当 1 件のみ・判定ログは 500 字で切断 |
| tool の結果 / errorText | ○（`state.output` / `state.error`） | ✗ |
| 時系列順序 | ○（`time_created` + `id`） | △ 書き込み系ツールのみの部分列 |
| system prompt | ✗ | ✗ |

- ✅ **deny 注入の実例が既に DB に残っている**（`state.error` に `[phase6] denied by judge (...)` の形で）。注入文字列の検証材料に使える
- ⚠ **`topology_corpusb.json` の absent 5 パス（既知の不整合 15）は DB の欠損ではない。** worktree の実体が消えている話であり、session DB は現存する（1619 ファイル）。**第 2 層の材料はこの制約を受けない**
- ⚠ **`callID` はグローバル一意ではない。** 同一セッション内での衝突を実測した（2471 件中 10 件）。対象の特定には `part.id` を使う

### 残作業・申し送り

3. ⚠ 超えないときは「材料を増やす / 反復を増やす / 確認的な主指標にしない」の 3 択。**「精度不足で判定不能」を正規の結末として認める**
4. リプレイ注入の実装と、(b) の機械分類器の `_layer2` へのコピー改修（⚠ **原本は改変しない**）
