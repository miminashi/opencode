# CLAUDE.md にプラン作成ルール新設 + レポート作成ルールへ執筆後チェック追加

## Context

`report/` 配下のレポートと `.claude/plans/` 配下のプランは、いずれも plan mode を経る作業の主要な文書アウトプットで、後日の追跡・再開時の第一資料になる。しかし初稿の時点では書き漏らしや前後で辻褄の合わない記述（例: 概要で「PASS」と書きつつ結果表では FAIL が混在、序盤で採用した命名を後半で別名に呼び替える、当初「不要」と書いた対象を後半で扱っているのに冒頭を更新し忘れる等）が入り込みやすい。実際、memory `project_fable_review_m33_2026_07_07.md` には m33 マージレポートの概要集計に取り違えがあり後段の表と食い違っていた（fable レビュー側で検出・訂正）事例が残っている。同種の破綻はプランでも起きうる（本セッションの初版プランで実際に「レポート作成を非対象」と書きつつ CLAUDE.md 冒頭のレポート必須ルールと矛盾していた）。

ユーザ要望は 2 種類の文書双方に「初稿後の再確認ステップ」をルール化すること:

1. **プラン**: 初稿完了後、プラン内に矛盾がないか再確認するステップを設ける（プラン作成ルール新設）。
2. **レポート**: 初稿完了後、(a) 記載漏れの追記 → (b) 矛盾チェック、の 2 ステップを設ける（既存レポート作成ルールへ追加）。

いずれも実コードには触れず、`CLAUDE.md` のみを更新する。

## 変更対象

- `/home/ubuntu/projects/opencode/CLAUDE.md`（コード変更対象はこの 1 ファイルのみ）
- `/home/ubuntu/projects/opencode/report/yyyy-mm-dd_hhmmss_plan_and_report_post_write_check.md`（後述「レポート作成」で作成）

現状の `CLAUDE.md` 構造（本編集に関係する範囲）:

- L110 `## レポート作成ルール`
  - L116 `### 保存先`

  - L127 `### レポート本文`
  - L144 `### 添付ファイル`（本文 L144–149）
  - L151 `### フォーマット例`

## 追加内容

### 変更 1: 新規セクション `## プラン作成ルール` を追加

挿入位置: `## レポート作成ルール`（L110）の**直前**。プランの作成はレポート作成に先行するワークフロー段階なので、時系列順に並べる。

追記する本文:

```markdown
## プラン作成ルール

plan mode でプランを書いた後、プラン内に矛盾がないか再度確認するステップを設ける。矛盾があれば正しい方に揃えて修正する（どちらが正しいか不明な場合は元の要件・調査結果・参照した既存コード等に立ち返って確定させる）。

チェック観点の例:

- 冒頭の Context / 目的と、後段の設計判断・非対象の切り分けが矛盾していないか
- 「変更対象」と実際の追加内容・検証手順で扱っている対象が食い違っていないか
- 既存ルール（CLAUDE.md 冒頭・memory 記載事項）と矛盾する前提を置いていないか
- プラン内で参照しているファイルパス・行番号・リンクが存在し、記載内容と整合しているか
```

### 変更 2: `## レポート作成ルール` に新規サブセクション `### 執筆後の確認` を追加

挿入位置: `### 添付ファイル` の末尾行（L149）と `### フォーマット例` の見出し行（L151）の間（L150 の空行位置）。

サブセクションを独立させる理由: 執筆完了後のワークフロー手順であり、本文の書き方ルール（`### レポート本文`）でも構造ルール（`### 添付ファイル`）でもない。フォーマット例より前に置くことで「例を見る前に必ず読む」順序を担保する。

追記する本文:

```markdown
### 執筆後の確認

レポートの初稿を書き終えたら、以下の 2 ステップを順に実施する:

1. **記載漏れの確認**: 作業内容・調査結果・実施したコマンド等を振り返り、レポートに書き忘れている事実がないか再確認する。書き漏らしがあれば追記する。
2. **矛盾点の確認**: 追記後の状態で、概要と各セクション、セクション間、本文と表・図等の間に矛盾がないか確認する。矛盾があれば正しい方に揃えて修正する（どちらが正しいか不明な場合は元データ・ログを再確認して確定させる）。

順序が重要: 先に (1) で事実を出揃えてから (2) で整合を取る。矛盾の解消を先にやると、追記で再び矛盾が生じる。
```

### 設計判断（両変更共通）

- プラン側は「矛盾チェックのみ」、レポート側は「記載漏れ + 矛盾チェック」と非対称にする — ユーザ要望に忠実に従うため（プランで記載漏れチェックが必要かは今回言及されていない。必要になれば後から追加すればよく、先回りしない）。
- プラン側の「チェック観点の例」は指針であって網羅チェックリストではない — 過度に厳密化してプラン作成コストを膨張させないため。
- レポート側の「順序が重要」を明示 — ユーザ要望の骨子（「記載し忘れた事実の確認**後**に矛盾を確認する」）を明文化するため。

## レポート作成

CLAUDE.md 冒頭「plan mode で作業の計画を立てる際は、レポートの作成を必ず作業内容に含めること」に従い、本変更もレポートを作成する（規模が小さくても plan mode で計画した作業である以上、例外にしない）。

- 作成先: `/home/ubuntu/projects/opencode/report/`
- ファイル名タイムスタンプは `TZ=Asia/Tokyo date +%Y-%m-%d_%H%M%S` で取得（LLM 推測禁止）
- レポート名: `plan_and_report_post_write_check`（英字・スネークケース）
- 本文に含める内容:
  - 追加の背景（プラン・レポート双方で発生しうる矛盾・記載漏れの実例、特に本セッション初版プランで実際に起きたレポート必須ルールとの矛盾を Case Study として記載）
  - 追加した 2 箇所の位置と、追加した本文の全文
  - 参照した既往事例（m33 レポート集計取り違えの memory エントリ）
- プランファイル本体を `report/attachment/<report_basename>/plan.md` にコピー（`.claude/plans/` は Read → Write で複製・`cp` 禁止）
- 新設した「執筆後の確認」の 2 ステップを、このレポート自身にも適用する（記載漏れチェック → 矛盾チェックの順）

## 検証

1. `CLAUDE.md` の該当箇所（`## プラン作成ルール` の見出し行を Grep で特定し、その周辺を Read）を確認:
   - `## プラン作成ルール` が `## レポート作成ルール` の直前に挿入されている
   - `### 執筆後の確認` が `### 添付ファイル` と `### フォーマット例` の間にある
   - 見出しレベル（`##` / `###`）と番号付きリスト・太字が壊れていない
2. Grep ツールで `^##+ ` を extended regex として実行し、次を目視確認:
   - `## プラン作成ルール` の下位に見出しなし（本文のみ）
   - `## レポート作成ルール` 配下のサブセクション順序が「保存先 → ファイル名 → レポート本文 → 添付ファイル → 執筆後の確認 → フォーマット例」
3. レポート成果物（`report/yyyy-mm-dd_hhmmss_plan_and_report_post_write_check.md`）と添付プラン（`report/attachment/<basename>/plan.md`）が存在すること、レポート本文冒頭の日時が JST 記載になっていることを確認。

## 非対象

- 既存の `### レポート本文`・`### フォーマット例`・memory 内テンプレート等の書き換えは行わない。
- 過去プラン・レポートを遡って本ルールで再チェックする作業は行わない（今後の新規プラン・レポートに適用）。
- プラン側への「記載漏れチェック」ステップ追加は行わない（今回のユーザ要望に含まれていないため）。
