## Context

phase 6（permission 判定役 LLM）の路線で、3 段構成（**段 1 指示から場所を抽出する LLM →
段 2 所属判定は機械 → 段 3 最終判断 LLM**）のうち段 1 だけを単体で測った結果が
[前回レポート](../../2026-08-06_001558_phase6_stage1_extraction.md)
にある。段 1 は事前登録した成立基準を North で満たし、規則が原理的に解けない
H 軸（参照専用の見分け）を 4 走行すべてで 11/11 取った。

一方で「指示された場所を拾う」（`cover_instructed`）は 76.7〜90.0% で、LLM 不使用の
`rule_regex`（100%）に判定不能帯を超えて負けた。生出力を調べると、失点の原因は
**雛形表現を扱えないことではなく、条件付き指示を「条件が確定しないので発動しない」と
読んでいること**だった。その条件（cwd が保護ブランチ上か）の判定に要る事実を
抽出器に渡していなかったため、**観測した 76.7〜90.0% が能力の天井なのか入力設計の
天井なのかが未確定**である。

本作業はこれを一意に切り分ける。**変更は雛形の 1 行だけ**（`current_directory の git
branch: main`）で、材料・probe・指標・成立基準・走行条件は一切変えない。

⚠ ユーザ方針（2026-08-06）: **LLM 単体の天井を先に確定させる。** 規則との
ハイブリッド（NEXT_SESSION.md 項目 3）は本作業の後。

## Step 1: 走行（約 6.5 時間）

**無人ラッパで丸ごと回す。** 22 時台の開始で完了は翌 04〜05 時になるため、
電源投入から後始末（unlock + 電源断）まで込みの `resume_stage1.sh` を使う。

```bash
systemd-run --user --unit=stage1v2 --collect --no-block -- \
  bash /home/ubuntu/projects/opencode/tmp/resume_stage1.sh
```

⚠ **必ず絶対パスで渡す。** `systemd-run --user` のユニットは cwd が `/home/ubuntu` で
起動する。相対パスだと即死し、**`--no-block` なので発行元にエラーが返らず、
`--collect` が失敗ユニットを消すため気づけない**。GPU を焚いたまま何も走らない事故になる。

⚠ **`run_stage1_v2_arms.sh` を直接叩かない。** これは GPU 起動も ready 待ちもしない。
ready 待ちを飛ばすと、モデルロード中に 12 arm 全部が数十秒で空振りし、
ユニットは `ALL DONE` で正常終了する（`run_stage1.py` の `health()` は落ちるが
ラッパは次の arm へ進むため）。

**走行内容**（本走 12 arm × 48 = 576 呼び出し・順次）:

| arm | 雛形 | 目的 |
|---|---|---|
| `{north,qwen}_stage1_rep3` | v1 | v1 を 3 周に揃える（集約どうしを比べるため） |
| `{north,qwen}_stage1_v2_rep1..3` | v2（branch あり） | **本命** |
| `{north,qwen}_stage1_cf_rep1..2` | v2 の branch を `work-stage1-cf` に | **反実仮想（非保護ブランチ）** |

走行条件は 1 回目と同一: `MAX_TOKENS=6144` / `TIMEOUT_MS=240000` / `TOKEN_CAP=6144` /
1 並列 / `temperature 0.6` / `top_p 0.95` / **`presence_penalty 0`**（サーバは
`--presence-penalty 1.0` で起動するのでリクエストで明示的に打ち消す）。

## Step 3: 採点（GPU 不要・保持済み raw.jsonl の純関数）

**本走 12 arm すべて**（cf 4 arm を含む）について `raw.jsonl` が 48 行あること、

### 3-3. 集約とノイズ床

```bash
AGG_GROUPS=v1_north:north_stage1_rep1,north_stage1_rep2,north_stage1_rep3+v2_north:... \
```

⚠ **判定不能帯は 1 回目に実測した 8.4pt をそのまま使う。** 3 周での実測も出すが、

### 3-4. ⚠ 反実仮想の両側採点（**片側だけで結論しない**）


## Step 4: 判定（事前登録 + 0-4 に従う。走行後に基準を動かさない）

| # | エンドポイント | 判定単位 |
|---|---|---|
| 1 | **A 軸の `cover_instructed`** が両モデルとも 5/6 以上 | **3 反復すべてで** 5/6 以上 |
| 1b | **B2 も回復する**（副次予測。B1/B2 は条件の有無だけが違う最小対） | **両モデル・3 反復すべて**（0-4 で確定） |
| 2 | 全体の `cover_instructed` が判定不能帯（8.4pt）を超えて改善 | rep 対 3 組と k=2 集約を全部併記し、**採否は k=2 集約で判定** |
| 3 | **他 3 指標が悪化しない**（`no_expand_silent` / `no_expand_lure` / `cover_cwd`） | 帯を超えて下がったら**採用しない** |
| 4 | 集約の効果（k=1 和集合 / k=2 多数決 / k=3 積集合）を v1・v2 両方で | 単発と集約を必ず併記 |
| 5 | 判定不能率 ≤ 15% | arm ごと（**cf 4 arm を含む**） |
| **3b** | **反実仮想の両側**: 条件付き 6 材料のうち**両側とも全 rep で正解した材料が 5 以上** | **材料単位・分母 6 固定**（0-4 で確定）。不変対照 A6・B1 が両側で 2/2 であることも確認 |

⚠ **3b が片側だけ高い場合、エンドポイント 1 を満たしても「入力設計の天井だった」とは
結論しない。**「常に出す」か「常に出さない」と区別できないため
（2026-08-05「片側だけ見ると一律 deny が満点を取る」の再適用）。
⚠ **不変対照が両側とも落ちるなら、原因は条件の適用ではなく branch 行そのものの副作用**である。

**中止条件**: 判定不能率 15% 超の arm は採点しない。エンドポイント 3 を落とした場合、
A 軸が回復していても **v2 は採用しない**（`ctxb_excl` / `ctxb_fact` と同じ
「狙った所は直ったが別の所が壊れた」型）。

## Step 5: レポート

0-1 で確定した名前でレポートを作成する。

- 冒頭に**概要**（平易な日本語の段落・5 段落目安）。**概要は Opus 4.7 が執筆する**
- 添付: `preregistration_v2_addendum.md`・本プラン・`save_stage1_outputs.py` の全出力

- 結果に応じて NEXT_SESSION.md を更新

**レポートに必ず書くこと**（fable 指摘 7・9・11）:

- **モデル間で結果が割れた場合の扱い。** North だけ回復・Qwen 未回復は 1 回目の水準差から
  十分あり得る。エンドポイント 1 の文言（両モデルとも）を**先に引いてから**数字を出す。
  「v1 より悪化」の行も同様に用意しておく
- **判定不能帯 8.4pt は単発 rep 対から導出したもので、k=2 集約どうしの比較に使うのは保守側に倒れる**
- **llama.cpp HEAD が 1 回目（`0843245cb`）と一致するか**（別日・サーバ再起動を挟む走行のため）
- **holdout が無く、同じ 48 文で 2 度目の選択をしている**こと。v2 採用の主張は
  「この材料集合上で」と限定される
- **粒度の限界**: A 軸の条件付きは 5 材料・B2 は 1 材料しかない。**1 材料 = 16.7pt** であり、
  5/6 という閾値は実質「1 材料まで許容」の意味である

| A 軸の結果 | 解釈 | 次 |
|---|---|---|
| 5/6 以上に回復 **かつ 3b 両側成立** | **入力設計の天井だった** | 難度の階段 L1〜L4（項目 2） |

## 検証方法

- **Step 0 の修正後**: `bash -n tmp/resume_stage1.sh` で構文検査。
  cleanup ガードは「lock を取れなかったときに unlock/power off を呼ばない」ことを
  スクリプトの読み合わせで確認する（実 GPU での失敗再現はしない）
- **走行開始直後**: 最初の arm が 5 分以内に 1 件以上 `raw.jsonl` へ書いているかを確認する。
